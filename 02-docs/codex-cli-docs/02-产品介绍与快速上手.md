Codex CLI 是 OpenAI 推出的终端编码代理，可在本地仓库中直接检查代码、执行修改、运行命令并自动化重复性工作，无需离开终端即可完成完整的开发闭环。本片涵盖 Codex CLI 的产品定位、安装与快速上手流程，以及官方推荐的使用最佳实践，帮助你从第一天起就建立高效、可复用的 Codex 工作流。

### 在终端中检查、编辑并运行代码

在终端中直接检查代码、做出修改、运行命令，并自动化重复性工作。

**从这里开始：**

- 安装 Codex
- CLI 参考（对应 [命令参考与自动化](03-命令参考与自动化.md)）

**为什么使用 Codex CLI：**

- **针对本地仓库工作：** 让 Codex 检查文件、执行编辑，并运行你机器上已安装的工具。
- **保持掌控：** 选择适合任务的模型、推理强度、权限和命令。
- **与脚本和 CI 组合使用：** 交互式使用 Codex，或在可重复的工作流和流水线中调用 `codex exec`。

### 快速上手

**开始使用 Codex CLI。**

安装 Codex、登录，并在项目目录中运行你的第一个任务。

**1. 安装 Codex**

选择以下任一安装方式：

macOS / Linux — 使用独立安装器：

```bash
curl -fsSL https://chatgpt.com/codex/install.sh | sh
```

更新同样使用上述命令。

Windows — 在新的 PowerShell 窗口中运行：

```powershell
powershell -ExecutionPolicy ByPass -c "irm https://chatgpt.com/codex/install.ps1 | iex"
```

更新同样使用上述命令。

npm：

```bash
npm install -g @openai/codex
```

更新同样使用上述命令。

Homebrew：

```bash
brew install --cask codex
```

更新：

```bash
brew upgrade --cask codex
```

**2. 运行 Codex 并登录**

打开项目目录并运行 `codex`。首次运行时，选择 **Sign in with ChatGPT** 或其他可用的登录方式。认证选项详见 /docs/auth。

**3. 开始第一个任务**

描述你想要完成的目标。例如，让 Codex 解释项目、做出聚焦的修改，或帮助调试问题：

```text
Tell me about this project
```

建议在任务前后创建 Git 检查点，以便回滚更改。参见下方的最佳实践。

- 浏览 CLI 参考（对应 [命令参考与自动化](03-命令参考与自动化.md)）
- 配置 Codex（对应 [配置-基础与示例](04-配置-基础与示例.md)）
- 使用 `codex exec` 自动化（对应 [命令参考与自动化](03-命令参考与自动化.md)）

### Codex CLI 能做什么

用一个聚焦的终端循环来处理交互式工作、自动化、审查和委派。

- **在终端中保持编码循环：** 在仓库中启动 Codex，探索不熟悉的代码、规划变更、编辑文件并运行本地开发工具。引导当前回合、查看出现的命令和 diff，并在同一会话中继续后续工作。
- **使用 skills 和 plugins：** 将可重复的指令打包为 skill，然后添加 plugin 将 Codex 连接到团队工具和数据，无需离开 CLI（对应 [扩展能力](09-扩展能力.md)）。
- **在变更交付前进行审查：** 对未提交的更改、某个 commit 或基础分支运行专门的审查。Codex 会报告按优先级排列的发现，而不修改你的工作树，让你在提交或发起 Pull Request 之前处理风险。

### 围绕 Codex 构建终端工作流

了解可用于恢复会话、添加视觉和 Web 上下文、拆分复杂工作以及将 Codex 连接到开发工具的 CLI 功能。

- **返回已保存的聊天** — `codex resume`：从当前仓库重新打开最近的聊天，或在需要返回更早的工作时搜索本地聊天。
- **将视觉上下文带入提示** — `codex --image`：在首次提示时附带错误截图、架构图或设计参考，或在交互式编辑器中粘贴图片。
- **拆分较大的调查** — `subagents`：让 Codex 将聚焦的工作委派给专门的 agent，然后将其发现带回主终端会话（对应 [Agent配置](06-Agent配置.md)）。
- **搜索当前上下文** — `codex --search`：当任务依赖于当前版本、文档或外部行为时，将运行切换为实时 Web 搜索。搜索活动在 transcript 中保持可见。
- **将工作移到 Codex 云端** — `codex cloud`：浏览活跃和已完成的聊天，将工作提交到已配置的环境，并从终端将结果应用到本地仓库。
- **使用 MCP 连接外部工具** — `codex mcp`：添加本地或远程 MCP 服务器，在需要时进行认证，并在 Codex 使用之前检查当前会话可用的工具（对应 [扩展能力](09-扩展能力.md)）。
- **设定每次运行的边界** — `/permissions`：选择 Codex 在何时可以无需询问即编辑文件或运行命令，并在继续之前检查活跃的沙箱和可写根目录（对应 [权限与安全](08-权限与安全.md)）。
- **让 Codex 适配你的终端** — `codex completion`：为 shell 生成补全，选择语法主题，并在由 VISUAL 或 EDITOR 配置的编辑器中打开较长的提示。

### 适合使用 Codex CLI 的场景

- 你在终端中工作：在一个聚焦的循环中探索、编辑和运行仓库。
- 你需要脚本或 CI：在可重复的工作流中运行非交互式命令（对应 [命令参考与自动化](03-命令参考与自动化.md)）。
- 你想要本地代码审查：在提交或发起 Pull Request 之前检查更改。
- 你想将工作交给云端：启动云端聊天，稍后返回终端。

## 最佳实践

原文存档：[source/best-practices.md](source/best-practices.md)

如果你是 Codex 或编码代理的新手，本指南将帮助你更快获得更好的结果。它涵盖了让 Codex 在 CLI、IDE 扩展和 ChatGPT 桌面应用中更有效的核心习惯，从提示和规划到验证、MCP、skills 和定时任务。

Codex 的最佳使用方式不是把它当作一次性助手，而是当作一个你持续配置和改进的队友。

一个有用的思考方式是：为任务提供正确的上下文、使用 `AGENTS.md` 持久化指导、配置 Codex 以匹配你的工作流、用 MCP 连接外部系统、将重复工作转化为 skill，并自动化稳定的工作流。

### 良好的首次使用：上下文与提示

Codex 已经足够强大，即使你的提示不够完美也能产出有用的结果。你通常可以用最少的设置把一个难题交给它，仍然得到不错的结果。清晰的提示技巧不是获得价值的前提，但它确实能让结果更可靠，尤其是在较大的代码库或高风险任务中。

如果你在一个大型或复杂的仓库中工作，最大的解锁点是为 Codex 提供正确的任务上下文和清晰的完成标准。

一个好的默认做法是在提示中包含四样东西：

- **目标（Goal）：** 你想要修改或构建什么？
- **上下文（Context）：** 哪些文件、文件夹、文档、示例或错误与本任务相关？你可以使用 @ 提及某些文件作为上下文。
- **约束（Constraints）：** Codex 应遵循哪些标准、架构、安全要求或约定？
- **完成条件（Done when）：** 任务完成前应满足什么条件，例如测试通过、行为改变、或某个 bug 不再复现？

这有助于 Codex 保持在范围内、减少假设，并产出更易于审查的工作。

在你的账户和客户端支持时使用 GPT-6.1 Sol，从客户端默认提供的推理强度开始。对于 GPT-6 Luna 从 **High** 开始，或对于 GPT-6 Astra 从 **Light**（配置中为 `low`）开始。根据任务和结果进行调整。可用推理级别参见 /codex/models：

- Low：用于更快的、范围明确的任务
- Medium 或 High：用于更复杂的变更或调试
- Extra High：用于长时间、代理式、推理密集的任务

为了更快地提供上下文，可以尝试在 ChatGPT 桌面应用中使用语音听写来描述你想让 Codex 做什么，而不是打字。

### 复杂任务先规划

如果任务复杂、模糊或难以清晰描述，让 Codex 在开始编码之前先做规划。

以下几种方法效果很好：

**使用 Plan 模式：** 对大多数用户来说，这是最简单也最有效的选项。Plan 模式让 Codex 收集上下文、提出澄清问题，并在实施之前构建更完善的计划。使用 `/plan` 或 Shift+Tab 切换。

**让 Codex 采访你：** 如果你大致知道想要什么但不确定如何描述，让 Codex 先向你提问。告诉它挑战你的假设，在写代码之前将模糊的想法变成具体的东西。

**使用 PLANS.md 模板：** 对于更高级的工作流，你可以配置 Codex 遵循 `PLANS.md` 或执行计划模板，用于较长时间或多步骤的工作。更多细节参见 /cookbook/articles/codex_exec_plans。

### 用 `AGENTS.md` 让指导可复用

一旦某种提示模式奏效，下一步就是停止手动重复它。这就是 `AGENTS.md` 的用武之地。

把 `AGENTS.md` 想象成一份面向 agent 的开放格式 README。它自动加载到上下文中，是编码你和团队希望 Codex 在仓库中如何工作的最佳位置（对应 [Agent配置](06-Agent配置.md)）。

一份好的 `AGENTS.md` 涵盖：

- 仓库布局和重要目录
- 如何运行项目
- 构建、测试和 lint 命令
- 工程约定和 PR 期望
- 约束和禁止规则
- "完成"意味着什么以及如何验证工作

CLI 中的 `/init` 斜杠命令是快速入门命令，可在当前目录中脚手架一份 starter `AGENTS.md`。这是一个很好的起点，但你应该编辑结果以匹配团队实际的构建、测试、审查和发布代码的方式。

你可以在不同层级创建 `AGENTS.md` 文件：位于 `~/.codex` 的全局 `AGENTS.md` 用于个人默认值，仓库级文件用于共享标准，以及子目录中更具体的文件用于局部规则。如果当前目录附近有更具体的文件，该指导优先。

保持实用。一份简短、准确的 `AGENTS.md` 比充满模糊规则的长文件更有用。从基础开始，仅在注意到重复错误后才添加新规则。

如果 `AGENTS.md` 开始变得过大，保持主文件简洁，并为规划、代码审查或架构等内容引用专门的 markdown 文件。

当 Codex 两次犯同样的错误时，让它做一次回顾并更新 `AGENTS.md`。指导保持实用且基于真实的摩擦点。

### 配置 Codex 以保持一致性

配置是让 Codex 在会话和界面之间行为更一致的主要方式之一。例如，你可以设置模型选择、推理强度、沙箱模式、审批策略、profiles 和 MCP 设置的默认值（对应 [配置-基础与示例](04-配置-基础与示例.md)）。

一个好的起始模式是：

- 个人默认值保存在 `~/.codex/config.toml`（ChatGPT 桌面应用中的 **Settings > Configuration > Open config.toml**）
- 仓库特定行为保存在 `.codex/config.toml`
- 命令行覆盖仅用于一次性情况（如果你使用 CLI）

`config.toml` 是定义持久偏好的地方，例如 MCP 服务器、多代理设置和功能开关。特定于 profile 的覆盖位于单独的 `$CODEX_HOME/profile-name.config.toml` 文件中。

Codex 自带操作系统级沙箱，有两个关键控制项：审批模式决定 Codex 何时请求你的许可来运行命令，沙箱模式决定 Codex 可以在目录中读取或写入什么以及 agent 可以访问哪些文件（对应 [权限与安全](08-权限与安全.md) 与 [环境与沙箱](07-环境与沙箱.md)）。

如果你是编码代理新手，从默认权限开始。默认保持审批和沙箱严格，仅在明确需要时为受信任的仓库或特定工作流放宽权限。

注意 CLI、IDE 扩展和 ChatGPT 桌面应用共享相同的配置层级。更多信息参见 /codex/config-file/config-sample（对应 [配置-基础与示例](04-配置-基础与示例.md)）。

尽早为你的真实环境配置 Codex。许多质量问题实际上是设置问题，例如错误的工作目录、缺少写入权限、错误的模型默认值，或缺少工具和连接器。

### 通过测试和审查提高可靠性

不要止步于让 Codex 做出修改。让它在需要时创建测试、运行相关检查、确认结果，并在你接受之前审查工作。

Codex 可以为你完成这个循环，但前提是它知道"好"是什么样的。该指导可以来自提示或 `AGENTS.md`。

这可以包括：

- 为变更编写或更新测试
- 运行正确的测试套件
- 检查 lint、格式化或类型检查
- 确认最终行为与请求匹配
- 审查 diff 以发现 bug、回归或风险模式

在 ChatGPT 桌面应用中切换 diff 面板以直接在本地审查更改。点击特定行可以提供反馈，作为上下文输入到 Codex 的下一个回合。

这里一个有用的选项是 `/review` 斜杠命令，它提供几种代码审查方式：

- 针对基础分支进行 PR 风格审查
- 审查未提交的更改
- 审查某个 commit
- 使用自定义审查指令

如果你和团队有一份 `code_review.md` 文件并从 `AGENTS.md` 中引用它，Codex 在审查时也可以遵循该指导。对于希望审查行为在仓库和贡献者之间保持一致的团队来说，这是一个强有力的模式。

Codex 不应只生成代码。有了正确的指令，它还可以帮助**测试它、检查它和审查它**。

如果你使用 GitHub Cloud，可以设置 Codex 为你的 PR 运行代码审查。在 OpenAI，Codex 审查 100% 的 PR。你可以启用自动审查，或让 Codex 在你 @Codex 时响应式审查。

### 使用 MCP 获取外部上下文

当 Codex 需要的上下文存在于仓库之外时使用 MCP。它让 Codex 连接到你已经使用的工具和系统，这样你就不必不断将实时信息复制粘贴到提示中。

Model Context Protocol（MCP）是一个用于将 Codex 连接到外部工具和系统的开放标准（对应 [扩展能力](09-扩展能力.md)）。

在以下情况使用 MCP：

- 所需上下文存在于仓库之外
- 数据频繁变化
- 你希望 Codex 使用工具而不是依赖粘贴的指令
- 你需要跨用户或项目的可重复集成

Codex 同时支持 STDIO 和 Streamable HTTP 服务器（带 OAuth）。

在 ChatGPT 桌面应用中，进入 **Settings > MCP servers** 查看自定义和推荐的服务器。通常 Codex 可以帮助你安装所需的服务器，你只需要问。你也可以在 CLI 中使用 `codex mcp add` 命令添加自定义服务器，指定名称、URL 和其他详情。

仅在工具能解锁真实工作流时才添加。不要一开始就接入你使用的每个工具。从一两个明显能消除你已经经常做的手动循环的工具开始，然后再扩展。

### 将重复工作转化为 skill

一旦某个工作流变得可重复，停止依赖长提示或反复来回。使用 skill 将指令打包在 `SKILL.md` 文件中，以及 Codex 应一致应用的上下文和支持逻辑。Skills 在 CLI、IDE 扩展和 ChatGPT 桌面应用之间通用（对应 [扩展能力](09-扩展能力.md)）。

保持每个 skill 聚焦于一项工作。从 2 到 3 个具体用例开始，定义清晰的输入和输出，并编写描述说明 skill 做什么以及何时使用。包含用户实际会说的触发短语。

不要试图一开始就覆盖所有边缘情况。从一个代表性任务开始，让它良好运行，然后将该工作流转化为 skill 并持续改进。仅在脚本或额外资产能提高可靠性时才包含它们。

一个好的经验法则：如果你不断重复使用同一个提示或纠正同一个工作流，它可能应该成为一个 skill。

Skills 对于以下经常性工作特别有用：

- 日志分类
- 发布说明起草
- 按清单进行 PR 审查
- 迁移规划
- 遥测或事件摘要
- 标准调试流程

`$skill-creator` skill 是脚手架第一个版本 skill 的最佳起点。在迭代期间保持第一个版本本地。当准备好广泛分享时，将其打包为 plugin。Skill 最重要的部分之一是描述，它应该说明 skill 做什么以及何时使用。

个人 skills 存储在 `$HOME/.agents/skills`，共享的团队 skills 可以签入仓库内的 `.agents/skills`。这对于新成员入职特别有帮助。

### 使用定时任务处理重复工作

一旦工作流稳定，你可以安排 Codex 在后台为你运行。在 ChatGPT 桌面应用中，定时任务让你为重复性工作选择项目、提示、节奏和执行环境（对应 [命令参考与自动化](03-命令参考与自动化.md)）。

从 **Scheduled** 页面创建定时任务。选择项目、提示、节奏，以及任务在专用 Git worktree 还是本地环境中运行。提示可以调用 skill。更多关于 Git worktree 的信息参见 /codex/environments/git-worktrees（对应 [环境与沙箱](07-环境与沙箱.md)）。

好的候选包括：

- 总结最近的 commit
- 扫描可能的 bug
- 起草发布说明
- 检查 CI 失败
- 生成站会摘要
- 按计划运行可重复的分析工作流

一个有用的规则：skills 定义方法，定时任务定义时间表。如果某个工作流仍需要大量引导，先将其转化为 skill。一旦可预测，安排它运行可以节省时间。

将定时任务用于反思和维护，而不仅仅是执行。审查最近的聊天、总结重复的摩擦点，并随时间改进提示、指令或工作流设置。

### 组织长时间运行的聊天

聊天会随时间积累上下文、决策和操作，因此妥善管理它们对质量有很大影响。

ChatGPT 桌面应用让你可以固定聊天和创建 worktree。如果你使用 CLI，以下斜杠命令特别有用：

- `/experimental`：切换实验性功能并添加到 `config.toml`
- `/resume`：恢复已保存的聊天
- `/fork`：在保留原始 transcript 的同时创建新聊天
- `/compact`：当聊天变长时，你想要早期上下文的摘要版本。Codex 也会自动压缩聊天
- `/subagents`：在当前聊天的 subagent 线程之间切换（对应 [Agent配置](06-Agent配置.md)）
- `/theme`：选择语法高亮主题
- `/apps`：在 Codex 中直接使用 ChatGPT apps
- `/status`：检查当前会话状态

每个连贯的工作单元保持一个聊天。如果工作仍是同一问题的一部分，留在同一个聊天中通常更好，因为它保留了推理轨迹。仅在工作真正分叉时才 fork。

使用 Codex 的 subagent 工作流将有界工作从主线程卸载。让主 agent 聚焦于核心问题，使用 subagent 处理探索、测试或分类等任务。

### 常见错误

初次使用 Codex 时需要避免的几个常见错误：

- 将持久规则堆在提示中，而不是移入 `AGENTS.md` 或 skill
- 不给 agent 提供关于如何最好运行构建和测试命令的细节，导致它无法看到自己的工作
- 在多步骤和复杂任务上跳过规划
- 在不了解工作流之前就给 Codex 对计算机的完全权限
- 在同一文件上运行实时任务而不使用 Git worktree
- 在手动运行可靠之前就安排重复性任务
- 将 Codex 视为必须逐步盯着的东西，而不是与你自己的工作并行使用
- 为整个项目使用一个聊天，而不是每个连贯结果一个聊天。这会导致上下文膨胀，随着时间推移结果变差
