本页覆盖 Codex 的运行位置与隔离模型：Local / Worktree / Cloud 三种环境的选择、本地环境的 setup scripts 与 actions 配置、Git worktree 的工作流与 Handoff 机制，以及沙箱（sandbox）的边界、权限模式与默认配置。读完后你应能判断 Codex 应在哪种环境里跑、如何为 worktree 准备依赖，以及如何通过 `sandbox_mode` 与 `approval_policy` 控制 agent 的自主程度。

## Codex 环境（运行位置与隔离）

原文存档：[source/environments-modes.md](source/environments-modes.md)

在 ChatGPT 桌面应用中，打开 ChatGPT 下拉菜单并选择 **Codex**。新建 Codex 会话时，需要选择它的运行位置：

- **Local**：直接在你当前的项目目录里工作。
- **Worktree**：把改动隔离在一个 Git worktree 中。详见 [Git worktrees](07-环境与沙箱.md#git-worktrees)。
- **Cloud**：从一个已发布的、可复用的环境中启动一个远程任务。需要先准备并发布仓库、依赖与工具，见站内路径 `/docs/environments/cloud-environments`。

Local 与 Worktree 两种会话都跑在你自己的电脑上。用 **Work in** 选择 **This computer** 或 **Cloud**。对于本地 Git 项目，单独的 **Worktree** 开关可以把改动与你当前的 checkout 隔离开。

Cloud 任务需要一个你有权访问的已发布环境。如果还没有，可以在 web 或桌面应用中新建一个，或请工作区管理员授予你对共享环境的访问权限。选择环境与创建/发布环境是两件独立的事：共享访问只让你使用该环境，并不授权你编辑它。

你也可以在 web 或移动端启动并继续 cloud 任务。在移动端打开 **Codex** 并选择一个已发布环境即可。

创建环境的方式：在 web 或桌面应用中新建任务，选择 **Work in** > **Cloud**，打开 **Select environment**，再选 **Create environment**。Codex 会检查你选中的仓库，在发布前协助你准备并测试其配置。

每个 Cloud 任务都有自己的工作文件。任务中的文件改动不会回写到可复用环境。要改变后续任务的起点，需要更新并重新发布该环境的 setup。

Cloud 任务使用其云环境内可用的文件与服务。你本机的本地文件、正在运行的进程、浏览器登录态、VPN 访问都不会自动带过去。

更多概念术语见站内路径 `/docs/prompting`。

## 本地环境（worktree 设置步骤）

原文存档：[source/local-environment.md](source/local-environment.md)

本地环境（Local environments）让你为 worktree 配置 setup 步骤，同时为项目定义常用操作（actions）。

本地环境仅在 ChatGPT 桌面应用的 Codex 中可用。配置或使用本地环境前，先选择 **Codex**。

通过 ChatGPT 桌面应用的设置面板（`codex://settings`）配置本地环境。你可以把生成的文件提交到项目 Git 仓库，与他人共享。

Codex 把这份配置存放在项目根目录下的 `.codex` 文件夹中。如果一个仓库里包含多个项目，请打开包含共享 `.codex` 文件夹的那个项目目录。

### Setup scripts

由于 worktree 跑在与本地会话不同的目录里，项目可能尚未完全就绪，可能缺少依赖或未签入仓库的文件。Setup scripts 会在 Codex 新建会话、创建新 worktree 时自动执行。

在脚本里放入任何为配置环境所需的命令，例如安装依赖或执行构建。

例如，TypeScript 项目可能想在 setup script 里先装依赖再做一次初始构建：

```bash
npm install
npm run build
```

如果 setup 与平台相关，可以为 macOS、Windows、Linux 分别定义 setup script 覆盖默认值。

### Actions

用 actions 定义常用任务，例如启动应用的开发服务器或运行测试套件。这些 action 会出现在 ChatGPT 桌面应用顶部栏，便于一键触发；它们在应用内置的集成终端中运行（见站内路径 `/docs/integrated-terminal`）。

Action 的好处是避免反复手敲"为项目触发一次构建"或"启动开发服务器"这类常用命令。一次性的快速调试可以直接用集成终端。

例如，Node.js 项目可以建一个名为 "Run" 的 action，脚本内容为：

```bash
npm start
```

如果 action 命令与平台相关，同样可为 macOS、Windows、Linux 分别定义脚本。

为每个 action 选一个图标，便于在顶部栏识别。

### Use built-in Git tools

在 Codex 中，ChatGPT 桌面应用为每个本地项目和 worktree 提供了常用 Git 控件。Diff 面板显示当前 checkout 的改动，并允许你为 Codex 添加行内评论让它处理。你可以在不离开应用的情况下：暂存或还原单个代码块、暂存或还原整个文件、提交改动、推送分支、创建 pull request。

应用未暴露的 Git 操作请用集成终端。要把并发改动与本地 checkout 隔离，请在 [Git worktrees](07-环境与沙箱.md#git-worktrees) 中启动任务。

## Git worktrees

原文存档：[source/git-worktrees.md](source/git-worktrees.md)

Worktree 让 Codex 在同一个项目里同时跑多个互不干扰的独立会话。仓库、worktree 与命令都留在包含该项目的电脑或远程开发环境中。你可以直接在 ChatGPT 桌面应用里操作，也可以在 ChatGPT 移动端使用 Codex，在已连接的电脑上启动、引导、批准并审查 worktree 会话。

对于 Git 仓库，定时任务（scheduled tasks，见站内路径 `/docs/automations`）可以跑在专用的后台 worktree 上，避免与你正在进行的工作冲突。在未做版本控制的项目中，定时任务直接跑在项目目录里。你也可以手动在 worktree 中启动会话，并用 Handoff 在 Local 与 Worktree 之间移动会话。

Worktree 本身并不在你手机上本地运行。ChatGPT 移动端只是远程操控你已连接电脑上的 Codex——仓库与 worktree 仍在那台电脑或它所用的远程开发环境中。下面这些面向桌面的说明，都适用于那台被连接的电脑。

### What's a worktree

Worktree 只在属于 Git 仓库的项目中可用，因为底层用的是 Git 原生的 git worktree。一个 worktree 等于为你的仓库创建了第二份拷贝（"checkout"）。每个 worktree 都有仓库里每个文件的独立副本，但它们共享同一份元数据（`.git` 文件夹），包括提交、分支等。这让你可以同时 checkout 并处理多个分支。

### Terminology

- **Local checkout**：你自己创建的那个仓库。在 ChatGPT 桌面应用中有时简称 **Local**。
- **Worktree**：由 ChatGPT 桌面应用从你的 local checkout 创建出来的 Git worktree。
- **Handoff**：在 Local 与 Worktree 之间移动一个会话的流程。Codex 会处理所需的 Git 操作，把你的工作安全地在两者之间迁移。

### Why use a worktree

1. 与 Codex 并行工作，而不打扰你当前的 Local 环境。
2. 在你专注前台工作时，把后台任务排队跑起来。
3. 之后当你准备好更直接地检视、测试或协作时，再把会话移到 Local。

### Getting started

Worktree 需要 Git 仓库。请确认你选中的项目位于某个仓库内。

1.  **选择 "Worktree"**
    在新建会话视图中，composer 下方选择 **Worktree**。也可以选一个[本地环境](07-环境与沙箱.md#本地环境worktree-设置步骤)，让它为 worktree 跑 setup scripts。

2.  **选择起始分支**
    在 composer 下方选择作为 worktree 基底的 Git 分支。可以是 `main` / `master`、某个特性分支，或你当前带有未暂存本地改动的分支。

3.  **提交 prompt**
    提交 prompt 后，Codex 基于你选的分支创建一个 Git worktree。默认情况下，Codex 处于 detached HEAD 状态（不把任何分支 checkout 出来）。

4.  **选择继续工作的位置**
    准备好之后，你可以继续直接在 worktree 上工作，或把会话 handoff 到 local checkout。Handoff 到 Local（或从 Local handoff 出去）会同时移动会话与代码，让你在另一个 checkout 里继续。

### Working between Local and Worktree

Worktree 在外观和使用感受上与 local checkout 几乎一致，差别在于它们在你工作流中的位置。可以把 Local 理解为前台、Worktree 理解为后台。Handoff 让你在两者之间移动会话。

底层上，Handoff 会处理在两个 checkout 之间安全迁移工作所需的 Git 操作。这一点很关键，因为 **Git 只允许一个分支在同一时间被一个地方 checkout**。如果你在某个 worktree 里 checkout 了一个分支，就**不能**同时在 local checkout 里再 checkout 它，反之亦然。

实际使用中有两条常见路径：

1. 只在 worktree 上工作（见下文 Option 1）。当你能直接在 worktree 上验证改动时这条路径最合适——例如你已经通过[本地环境 setup script](07-环境与沙箱.md#本地环境worktree-设置步骤)装好了依赖与工具。
2. 把会话 handoff 到 Local（见下文 Option 2）。当你想把会话拉到前台时使用——例如你想在自己常用的 IDE 里检视改动，或者只能跑一个应用实例。

#### Option 1: Working on the worktree

如果你想始终留在 worktree 上完成改动，用会话头部的 **Create branch here** 按钮把当前 worktree 转成一个分支。

之后你就可以提交改动、把分支推送到远端仓库，并在 GitHub 上发起 pull request。

你也可以用头部的 "Open" 按钮把 IDE 打开到该 worktree，使用集成终端，或在 worktree 目录里做任何其他需要做的事。

记住：一旦你在某个 worktree 上创建了分支，就不能在任何其他 worktree（包括 local checkout）里再 checkout 它。

#### Option 2: Handing a chat off to Local

如果你想把会话拉到前台，在会话头部选择 **Hand off**，把它移到 **Local**。

当你想在常用 IDE 窗口里阅读改动、跑已有的开发服务器，或在你日常使用的同一环境里验证工作时，这条路径很合适。

Codex 会处理在 worktree 与 local checkout 之间安全迁移会话所需的 Git 步骤。

每个会话在生命周期内绑定同一个 worktree。如果你之后把会话再 handoff 回 worktree，Codex 会把它送回原来那个后台环境，让你从上次停下的地方继续。

你也可以反方向操作。如果你已经在 Local 里工作、想腾出台面，用 **Hand off** 把会话移到 worktree。当你想让 Codex 在后台继续干、自己切回本地做别的事时，这很有用。

由于 Handoff 基于 Git 操作，`.gitignore` 里的文件不会随会话一起迁移——除非 Codex 通过 `.worktreeinclude` 把它们复制进本地 managed worktree。

### Advanced details

#### Codex-managed worktrees

默认情况下，会话使用 Codex 托管的 worktree。这种 worktree 被设计得轻量、用完即弃。一个 Codex 托管的 worktree 通常专属于一个会话；如果你之后把会话 handoff 回来，Codex 会把它送回同一个 worktree。

#### How Codex manages worktrees for you

Codex 在 `$CODEX_HOME/worktrees` 下创建 worktree。起始提交是你在新建会话时所选分支的 `HEAD` 提交。如果你选了一个带有本地改动的分支，Codex 也会把这些未提交改动应用到 worktree 上。worktree 不会被 checkout 成某个分支，而是处于 detached HEAD 状态。这样 Codex 可以创建多个 worktree 而不污染你的分支列表。

#### Copy ignored local files into managed worktrees

本地 Codex 托管的 worktree 从一次 Git checkout 起步，所以被追踪的文件都在。如果你的仓库用 `.gitignore` 忽略了某些新 worktree 需要的本地 setup 文件，可以在仓库根目录加一个 `.worktreeinclude` 文件，列出要在 Codex 创建 managed worktree 时复制过去的被忽略路径或 `.gitignore` 风格的 pattern。

用于那些 Git 有意忽略的文件，例如 `.env`、`.env.local`、`config/secrets.json`。Codex 只复制匹配 `.worktreeinclude` 的被忽略文件，不会复制其他 Git 未追踪的本地文件。不要在里面列出已被追踪的文件。

Codex 会自动把被忽略的 `AGENTS.override.md` 复制进本地 managed worktree，无需在 `.worktreeinclude` 里再列。

```text
# .worktreeinclude
.env
.env.local
config/secrets.json
```

Codex 会跳过源端符号链接，也不会覆盖新 checkout 里已存在的文件。该行为只适用于 ChatGPT 桌面应用本地 managed worktree，不适用于远程 worktree，也不适用于你自己从命令行创建的 Git worktree。

#### Branch limitations

假设 Codex 在某个 worktree 上完成了工作，你用 **Create branch here** 在上面创建了 `feature/a` 分支。现在你想在 local checkout 上试一下。如果你去 checkout 这个分支，会看到如下错误：

```
fatal: 'feature/a' is already used by worktree at '<WORKTREE_PATH>'
```

要解决，你需要在 worktree 上先把 `feature/a` 换成另一个分支，然后才能在 local checkout 里 checkout 它。

如果你打算在本地 checkout 这个分支，用 Handoff 把会话移到 Local，而不是试图让同一个分支同时被两边 checkout。

> 为什么有这个限制：Git 不允许同一个分支同时被多个 worktree checkout，因为一个分支代表一个可变引用（`refs/heads/<name>`），其含义是"某个工作树当前 checkout 的状态"。分支被 checkout 时，Git 认为它的 HEAD 归那个 worktree 所有，并期望 `git commit`、`git reset`、`git rebase`、`git merge` 等操作以可预测的串行方式推进该引用。如果允许多个 worktree 同时 checkout 同一分支，就会产生歧义与竞争：到底哪个 worktree 的操作更新这个分支引用？可能导致提交丢失、索引不一致或冲突解决不清。通过强制"一个分支同一时间只属于一个 worktree"，Git 保证每个分支有唯一权威的工作副本，同时允许其他 worktree 以 detached HEAD 或在别的分支上安全地引用同样的提交。

#### Worktree cleanup

Worktree 会占用不少磁盘空间：每个 worktree 都有自己的一套仓库文件、依赖、构建缓存等。因此 ChatGPT 桌面应用会把 worktree 数量控制在一个合理上限。

默认情况下，Codex 保留最近 15 个 Codex 托管的 worktree。你可以在设置里修改这个上限，或关闭自动删除，自己管理磁盘占用。

Codex 会尽量避免删除仍重要的 worktree。Codex 托管的 worktree 在以下情况不会被自动删除：

- 有被置顶（pinned）的会话绑定它；
- 会话仍在进行中。

早期版本创建的 permanent worktree 仍然保留，并受自动清理保护。但项目菜单里已不再允许新建 permanent worktree。

Codex 托管的 worktree 在以下情况会被自动删除：

- 你归档了关联的会话；
- Codex 需要删除更老的 worktree 才能维持你配置的上限。

在删除 Codex 托管的 worktree 之前，Codex 会先在它上面保存一份工作快照。如果一个会话的 worktree 已被删除，你再打开它时会看到恢复选项。

### Frequently asked questions

- **能否控制 worktree 创建在哪里？** 可以。Codex 默认在 `$CODEX_HOME/worktrees` 下创建 managed worktree。要换位置，打开 **Settings > Worktrees**，修改 **Worktree root**。
- **能否在 Local 与 Worktree 之间移动会话？** 可以。用会话头部的 **Hand off** 在 local checkout 与 worktree 之间移动会话。Codex 会处理所需的 Git 操作，安全地把会话在两个环境间迁移。如果你之后再 handoff 回 worktree，Codex 会把它送回原来那个关联的 worktree。
- **worktree 被删除后，会话会怎样？** 即使底层 worktree 目录被删，会话仍可保留在历史里。对于 Codex 托管的 worktree，Codex 在删除前会保存快照，你重新打开关联会话时会提供恢复选项。

## 沙箱

原文存档：[source/sandboxing.md](source/sandboxing.md)

沙箱（sandbox）是一道边界：它让 agent 能自主行动，但又不把整台机器无限制地交给它。当一个本地会话在 **ChatGPT 桌面应用**、**Codex CLI** 或 **IDE 扩展**里运行命令时，这些命令默认跑在一个受限环境中，而不是以完全访问权限直接跑。

这个环境定义了 agent 能自主做什么：可以改哪些文件、命令能不能用网络。当任务留在这些边界内时，agent 可以一路推进而不停下来要确认；一旦需要越界，就走审批流。

沙箱与审批是两套协同工作的不同控制：沙箱定义技术边界，审批策略决定 agent 必须在何时停下来、在越界前先询问。

### What the sandbox does

沙箱不仅作用于内置文件操作，也作用于被 spawn 出来的命令。如果 agent 运行 `git`、包管理器、测试运行器等工具，这些命令同样继承沙箱边界。

Codex 在每个操作系统上使用平台原生的强制机制。macOS、Linux、WSL2、原生 Windows 的实现各不相同，但理念一致：给 agent 一个有边界的工作场所，让常规任务能在清晰的限制内自主运行。

### Why it matters

沙箱降低了审批疲劳。agent 不必为每个低风险命令都找你确认——它可以在你已经批准的边界内读文件、改文件、跑常规项目命令。

它也为 agentic 工作给出了更清晰的信任模型：你信任的不只是 agent 的"意图"，而是"agent 被强制限制在边界内运行"。这样更容易放手让 agent 独立干活，同时清楚知道它什么时候会停下来求助。

### Getting started

默认的权限模式会自动启用沙箱。

#### Prerequisites

在 **macOS** 上，沙箱开箱即用，基于内置的 Seatbelt 框架。

在 **Windows** 上，当你在 PowerShell 里运行时 Codex 使用原生 Windows 沙箱；在 WSL2 里运行时使用 Linux 沙箱实现。详见站内路径 `/docs/windows/windows-sandbox`。

在 **Linux 与 WSL2** 上，先用包管理器安装 `bubblewrap`：

Ubuntu/Debian：

```bash
sudo apt install bubblewrap
```

Fedora：

```bash
sudo dnf install bubblewrap
```

Codex 使用 `PATH` 上找到的第一个 `bwrap` 可执行文件。如果找不到 `bwrap`，Codex 会回退到一个内置 helper，但该 helper 需要系统支持创建非特权 user namespace。发行版包提供的 `bwrap` 能让这套机制更可靠。

当 `bwrap` 缺失、或 helper 无法创建所需 user namespace 时，Codex 会在启动时给出警告。在限制了该 AppArmor 设置的发行版上，建议加载 `bwrap` 的 AppArmor profile，让 `bwrap` 继续工作，而不是全局关闭该限制。

**Ubuntu AppArmor 注意事项**：在 Ubuntu 25.04 上，从 Ubuntu 软件仓库安装 `bubblewrap` 通常无需额外 AppArmor 设置即可工作。`bwrap-userns-restrict` profile 由 `apparmor` 包提供，位于 `/etc/apparmor.d/bwrap-userns-restrict`。

在 Ubuntu 24.04 上，安装 `bubblewrap` 后 Codex 仍可能警告无法创建所需 user namespace。请复制并加载额外 profile：

```bash
sudo apt update
sudo apt install apparmor-profiles apparmor-utils
sudo install -m 0644 \
  /usr/share/apparmor/extra-profiles/bwrap-userns-restrict \
  /etc/apparmor.d/bwrap-userns-restrict
sudo apparmor_parser -r /etc/apparmor.d/bwrap-userns-restrict
```

`apparmor_parser -r` 会把 profile 加载进内核而无需重启。你也可以重载所有 AppArmor profile：

```bash
sudo systemctl reload apparmor.service
```

如果该 profile 不可用或仍未解决问题，可以用下面命令关闭 AppArmor 对非特权 user namespace 的限制：

```bash
sudo sysctl -w kernel.apparmor_restrict_unprivileged_userns=0
```

#### 用 Work Cloud 访问本机

对于"通过 Work Cloud 访问本机"的任务，OpenAI 的云端负责协调对话。沙箱限制取决于每一步在哪里执行：

- **云端执行**：Work cloud 容器沿用既有 Work Cloud 策略。桌面浏览器站点规则不会自动套用到云端浏览器。
- **本机执行**：已支持的本机执行要求适用于连接电脑上的步骤。

对于带本机访问的 Work 与 dots，当启用托管策略时，受支持的全局策略会作用于共享的云端编排器。Work cloud 容器与 dots 云电脑使用各自的执行配置与要求。请分别测试本机与云端执行，确认各环境里到底哪套控制生效——一个环境的策略不会把访问权带给另一个环境。

在一个策略内部，从高到低的优先级为：OS 专属环境覆盖 → 全 OS 环境覆盖 → Global。更高优先级的策略胜出，即使低优先级策略看起来更具体。对于本机执行，MDM 与旧版托管设备要求优先于 Agent Security，后者又优先于设备自身的系统要求文件。

字段级合并规则与运行时上限见站内路径 `/docs/enterprise/managed-configuration`；生效的文件与网络限制分别见 `/docs/enterprise/chatgpt-work-local-security` 与 `/docs/enterprise/chatgpt-work-cloud-security`。

### How permissions work

用你所在 surface 的权限控件来调整 Codex 处理本地动作的方式。

审批决定 Codex 在一个动作前何时暂停；沙箱决定命令能访问哪些文件与网络资源。当一个审批提供不同范围（例如"本次批准"或"本次会话内批准"）时，选能让任务继续推进的最窄范围。默认保持项目边界；不要为了跨无关仓库而放宽访问，而是改用单独的项目或 worktrees。

**ChatGPT web 端**：在托管的隔离环境中运行代码与 shell 命令。工作区策略与工具级控件决定可用能力。当设置可用时，用 **Settings > Data controls > Work network access** 管理代码与 shell 命令的网络访问。打开 **Allow public internet access** 让这些命令能访问公网；关闭时命令只能访问托管 allowlist 中的必要主机名。网页搜索、插件与远程浏览器有各自独立的控制。改动在当前代码或 shell 运行结束、Work 刷新执行环境后生效。ChatGPT web 不暴露本地 Codex 沙箱或审批模式选择器。

**ChatGPT 桌面应用**：用 composer 下方的权限控件。根据你的配置，菜单可能包含 **Ask for approval**、（对合格审批请求的）**Approve for me**、**Full access**，以及命名的或自定义的权限 profile。

**Codex CLI**：在 CLI 中输入 `/permissions` 打开权限选择器，切换当前生效的权限 profile（详见 [03-命令参考与自动化](03-命令参考与自动化.md)）。

**IDE 扩展**：用 composer 下方的权限控件。根据你的配置，菜单可能包含 **Ask for approval**、（对合格审批请求的）**Approve for me**、**Full access**，以及命名的或自定义的权限 profile。

### Configure defaults

要让每次启动都保持同样行为，在 `config.toml` 里设置默认值。工作原理见 [04-配置-基础与示例](04-配置-基础与示例.md)；`sandbox_mode`、`approval_policy`、`approvals_reviewer`、`sandbox_workspace_write.writable_roots` 这些键的完整说明见 [05-配置-高级与参考](05-配置-高级与参考.md)。用这些设置决定：agent 默认有多大自主权、能写哪些目录、何时该暂停等待审批、以及谁来审查合格的审批请求。

常见沙箱模式概览：

| 沙箱模式 | 含义 |
| --- | --- |
| `read-only` | agent 可以检视文件，但不能改文件，也不能未经批准就运行命令。 |
| `workspace-write` | agent 可以读文件、在 workspace 内编辑、并在该边界内运行常规本地命令。这是本地工作的默认低摩擦模式。 |
| `danger-full-access` | agent 不受沙箱限制运行。这会去掉文件系统与网络边界，只在你确实想让 agent 完全访问时使用。 |

常见审批策略：

| 审批策略 | 含义 |
| --- | --- |
| `on-request` | agent 默认在沙箱内工作，需要越界时才询问。 |
| `never` | agent 不停下来弹审批。 |

Codex 与 ChatGPT Work 不再把 `untrusted` 作为可选的审批策略。如果既有配置仍使用该值，请迁移：见站内路径 `/docs/agent-approvals-security`，并参考 [08-权限与安全](08-权限与安全.md)。

当审批是交互式的时候，你还可以用 `approvals_reviewer` 选择由谁来审查：

- `user`：审批提示交给用户。默认值。
- `auto_review`：合格的审批请求交给一个 reviewer agent（见站内路径 `/docs/sandboxing/auto-review` 的 automatic review）。

完全访问等于 `sandbox_mode = "danger-full-access"` 配合 `approval_policy = "never"`。作为对照，更低风险的本地自动化预设是 `sandbox_mode = "workspace-write"` 配合 `approval_policy = "on-request"`，对应的 CLI flag 是 `--sandbox workspace-write --ask-for-approval on-request`。之后你可以保留 `approvals_reviewer = "user"` 走人工审批，或设为 `approvals_reviewer = "auto_review"` 走自动审批审查。

如果你需要 agent 跨多个目录工作，writable roots 可以在不拆掉整个沙箱的前提下扩展它能修改的位置。如果你需要更宽或更窄的信任边界，应调整默认沙箱模式与审批策略，而不是依赖一次性例外。

当某个工作流确实需要特定例外时，用 rules。rules 让你在沙箱之外对命令前缀执行 allow / prompt / forbid，这通常比大幅放宽访问更合适。rules 的配置见 [06-Agent配置](06-Agent配置.md)。IDE 专属的设置入口见站内路径 `/docs/developer-settings`。

自动审查（在可用时）并不改变沙箱边界。它只是边界处审批请求的一种 `approvals_reviewer` 选项，例如沙箱升级请求、被拦截的网络访问、或仍需审批的有副作用工具调用。已经在沙箱内允许的动作不会被额外审查。reviewer 生命周期、触发类型、拒绝语义与配置细节见站内路径 `/docs/sandboxing/auto-review`。

平台细节见各平台专属文档。原生 Windows 的 setup、行为与故障排查见站内路径 `/docs/windows/windows-sandbox`。管理员要求与组织级别的沙箱/审批约束见 [08-权限与安全](08-权限与安全.md)。
