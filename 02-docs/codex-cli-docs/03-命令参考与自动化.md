# 命令参考与自动化

本页汇总 Codex CLI 的命令行入口、非交互执行方式、GitHub Action 集成、终端外观定制以及生命周期 Hooks 扩展。读完本页后，你应当能够在终端里选择合适的子命令、在 CI 里以 `codex exec` 跑自动化任务、通过 `openai/codex-action` 在 PR 上触发 Codex 评审，并用 Hooks 在工具调用前后插入自定义策略。配置项的完整字典见后续「05-配置-高级与参考」分片，基础示例见 [04-配置-基础与示例](04-配置-基础与示例.md)。

## CLI 命令参考

原文存档：[source/developer-commands.md](source/developer-commands.md)

本页是 Codex CLI 全部子命令与 flag 的索引。CLI 大多数默认值来自 `~/.codex/config.toml`，命令行传入的 `-c key=value` 仅当次生效并覆盖配置文件；配置优先级细节见 [04-配置-基础与示例](04-配置-基础与示例.md)。成熟度标签（Experimental / Beta / Stable / Deprecated）的含义在后续「10-故障排查」分片中说明。

### 全局 flag 与命令概览

全局 flag 作用于基础 `codex` 命令，多数会向下传递到子命令（例如 `codex exec --oss ...` 会把 `--oss` 应用到 `exec`）。命令概览表给出每个子命令的成熟度；下面按子命令说明用途。

### 常用子命令

- **`codex`（交互 TUI）**：不带子命令直接运行即启动交互式终端 UI。除全局 flag 外还接受图片附件；Web 搜索默认走缓存模式，用 `--search` 切换到实时浏览。本地低摩擦场景推荐 `--sandbox workspace-write --ask-for-approval on-request`。通过 `--remote ws://host:port`（或 `wss://`、`unix://`）可把 TUI 连到 `codex app-server --listen` 起的服务端；需要 Bearer 令牌时配合 `--remote-auth-token-env <ENV_VAR>`。
- **`codex agents`**：打开命令中心，浏览共享服务器上的会话并切换 agent。用 `--remote <URL>` 连远端、`--cd <DIR>` 为新远端任务指定目录；不支持 `--no-daemon`。
- **`codex queue`**：向已有会话投递一条文本消息：
  ```bash
  codex queue --thread <SESSION_ID> --message "Run the remaining checks"
  ```
  `--thread` 接受 UUID 或精确会话名（重名时用 UUID）。也支持 `--remote` 与 `--remote-auth-token-env`，不支持图片附件。
- **`codex app-server`**：本地启动 Codex app 服务器，主要用于开发调试。`--listen stdio://`（或别名 `--stdio`）保留默认 JSONL-over-stdio；`--listen ws://IP:PORT` 启用 WebSocket（对外 `wss://` 需自行 TLS 终结）；`--listen unix://` 走默认 Unix socket，或 `--listen unix:///absolute/path.sock` 指定路径。生成客户端绑定 schema 时加 `--experimental`。`--code-mode-host wss://host/host` 可把 app-server 连到远端 Code Mode 宿主。
- **`codex remote-control`**：在符合条件时通过托管后台服务器启动远程控制，前台作为兜底。`--no-daemon` 显式前台运行；`start` / `stop` 管理本地 app-server 守护进程；`pair` 生成短时人工配对码（加 `--json` 返回 `pairingCode`、`manualPairingCode`、`environmentId`、`expiresAt`）。`--no-daemon` 只用于裸 `remote-control`，不要与 `start`/`stop`/`pair` 组合。
- **`codex app`**：在 macOS / Windows 上从终端拉起 ChatGPT 桌面应用；macOS 可直接打开工作区路径，Windows 打印待打开的路径。
- **`codex debug app-server send-message-v2`**：用内置测试客户端走一遍 app-server V2 的 thread/turn 流程，本地复现协议行为。
- **`codex debug models`**：打印 Codex 看到的模型目录 JSON；`--bundled` 只看二进制内置目录而不刷新远端。
- **`codex debug prompt-input`**：把模型实际看到的 prompt 输入列表以 JSON 渲染出来，用于调试指令发现、会话上下文与 prompt 构造。
- **`codex apply`**：把 Codex 云端聊天里最近一次 diff 应用到本地仓库（需已登录且有权访问该聊天）。`git apply` 失败时（例如冲突）打印被打补丁的文件并以非零码退出。
- **`codex review`**：非交互跑代码评审。`--uncommitted`、`--base`、`--commit` 与自定义 `PROMPT` 互斥；`--title` 只能与 `--commit` 合用。
- **`codex archive` / `codex unarchive`**：按会话 ID 或会话名归档 / 恢复已保存的交互会话，ID 优先于名字。
  ```bash
  codex archive <SESSION>
  codex unarchive <SESSION>
  ```
- **`codex delete`**：永久删除已保存会话。`--force` 只能配合 UUID 使用；命名会话仍需交互确认。
  ```bash
  codex delete <SESSION>
  codex delete <SESSION_UUID> --force
  ```
- **`codex cloud`**：从终端操作 Codex 云端聊天。默认打开交互选择器；`codex cloud exec` 直接提交任务；`codex cloud list` 返回近期聊天（`--json` 输出 `tasks` 数组与可选 `cursor`，每个 task 含 `id`、`url`、`title`、`status`、`updated_at`、`environment_id`、`environment_label`、`summary`、`is_review`、`attempt_total`）。认证复用主 CLI 凭据；任务提交失败以非零码退出。
- **`codex completion`**：生成 shell 补全脚本，例如 `codex completion zsh > "${fpath[1]}/_codex"`。
- **`codex doctor`**：在报障前生成本地诊断报告，覆盖安装、配置、认证、运行时、Git、终端、app-server、线程清单等健康项。
- **`codex features`**：管理 `$CODEX_HOME/config.toml` 里的 feature flag；`enable` / `disable` 会持久化；不接受 `--profile`。
- **`codex exec`**：脚本化 / CI 风格的非交互运行（详见本页「非交互模式」一节）。可加 `--json` 输出逐行 JSON 事件；`resume` 子命令继续非交互任务，`--last` 取当前工作目录最近会话，`--all` 跨所有会话查找。`codex exec fork <SESSION_ID> [PROMPT]` 把已存会话复制成新会话；prompt 传 `-` 表示从 stdin 读取，`--image` 附加图片。使用图片、`--output-schema`、`--output-last-message` 或 `--ephemeral` 时必须给 prompt。`--worktree` 在托管 Git worktree 中跑（要求本地执行，不要与 `resume`、`review`、`--ephemeral`、`--ignore-user-config` 合用）：
  ```bash
  codex exec --worktree "implement the next step"
  codex exec fork <SESSION_ID> --worktree "try an alternative approach"
  ```
- **`codex execpolicy`**：保存前检查 `execpolicy` 规则文件。`codex execpolicy check` 接受一个或多个 `--rules`（例如 `~/.codex/rules` 下文件），输出最严决策与命中规则的 JSON；`--pretty` 美化输出。目前处于 preview。
- **`codex login` / `codex logout`**：用 ChatGPT 账号、API key 或访问令牌认证；不带 flag 时打开浏览器走 OAuth。`codex login status` 在有凭据时退出码为 `0`，便于自动化脚本判断。`logout` 清除两类凭据，无 flag。
- **`codex mcp`**：管理 `~/.codex/config.toml` 中的 MCP server 条目；`add` 同时支持 stdio 与 streamable HTTP 传输；OAuth 动作（`login`、`logout`）仅对支持 OAuth 的 streamable HTTP server 生效。
- **`codex plugin`**：从配置的 marketplace 安装、列出、移除插件。`add --json` 输出 `pluginId`、`name`、`marketplaceName`、`version`、`installedPath`、`authPolicy`；`list --json` 输出 `installed` 与 `available` 数组；`remove --json` 输出 `pluginId`、`name`、`marketplaceName`。
- **`codex plugin marketplace`**：管理插件 marketplace 源。`add` 接受 GitHub 简写 `owner/repo` 或 `owner/repo@ref`、HTTP(S) Git URL、SSH Git URL、本地根目录；`--ref` 固定 Git 引用，可重复 `--sparse PATH` 做稀疏检出。`list` 打印生效 marketplace 名与根。各子命令加 `--json` 输出自动化友好字段。
- **`codex mcp-server`**：该命令与独立 `codex-mcp-server` 二进制已移除，请改用 app-server（站内对应路径 /docs/app-server）。
- **`codex resume`**：按 ID 继续交互会话，或恢复最近一次聊天。`--last` 默认限定当前工作目录，加 `--all` 跨全部会话；接受模型与沙箱覆盖，但不支持 `--worktree`。当前目录与会话保存目录不一致时会询问；把 `tui.resume_cwd` 设为 `"current"` 或 `"session"` 可免提示；显式 `--cd`（`-C`）优先级最高。
- **`codex fork`**：把已有交互会话分叉成新聊天。默认打开选择器；`--last` 分叉最近一次。工作目录询问与 `tui.resume_cwd` 行为同 `resume`。`codex fork <SESSION_ID> --worktree` 在托管 Git worktree 中分叉（需显式会话 ID 与本地执行，不支持 `--last` 与选择器）。
- **`codex sandbox`**：沙箱助手，以 Codex 内部同样的策略运行命令。macOS seatbelt、Linux Landlock、Windows 各有一组 flag。
- **`codex update`**：在支持自更新的发行版上检查并应用更新；debug 构建会提示改用 release 构建。

### flag 组合与安全建议

- 无人值守的本地任务用 `--sandbox workspace-write`；除非在专用沙箱 VM 内，否则避免 `--dangerously-bypass-approvals-and-sandbox`。
- 需要让 Codex 写更多目录时优先 `--add-dir`，不要轻易 `--sandbox danger-full-access`。
- CI 中把 `--json` 与 `--output-last-message` 配对使用，同时拿到机器可读进度与最终自然语言摘要。

### 交互 TUI 快捷键

- 输入 `@` 在工作区搜索文件并把路径加入 prompt。
- <kbd>Up</kbd> / <kbd>Down</kbd> 恢复草稿历史；<kbd>Ctrl</kbd>+<kbd>R</kbd> 搜索 prompt 历史，<kbd>Enter</kbd> 采用、<kbd>Escape</kbd> 取消。
- <kbd>Ctrl</kbd>+<kbd>O</kbd> 或 `/copy` 复制最近一次完成的 Codex 输出。
- 行首加 `!` 在当前审批与沙箱设置下跑本地 shell 命令。
- Codex 工作时按 <kbd>Tab</kbd> 把后续 prompt、斜杠命令或 shell 命令排队到下一回合；按 <kbd>Enter</kbd> 把新指令注入当前回合。
- 空输入框按两次 <kbd>Escape</kbd> 编辑上一条用户消息并从此处分叉聊天。
- <kbd>Ctrl</kbd>+<kbd>C</kbd> 或 `/exit` 关闭会话。

## 非交互模式（codex exec）

原文存档：[source/non-interactive-mode.md](source/non-interactive-mode.md)

`codex exec`（简写 `codex e`）让你在脚本或 CI 里跑 Codex 而不打开 TUI。flag 级细节见上一节 CLI 命令参考；本站内相关路径 /docs/developer-commands 与 /docs/github-action 对应本资料集相应章节。

### 何时使用

适合：作为流水线一环（CI、合并前检查、定时任务）；产出可管道给其他工具的结果（发版说明、摘要）；串成 CLI 工作流；以显式、预设的沙箱与审批策略运行。

### 基本用法

任务 prompt 作为单个参数传入：

```bash
codex exec "summarize the repository structure and list the top 5 risky areas"
```

运行时 Codex 把进度流式输出到 `stderr`，只把最终 agent 消息打到 `stdout`，便于重定向或管道：

```bash
codex exec "generate release notes for the last 10 commits" | tee release-notes.md
```

不希望把会话 rollout 文件落盘时加 `--ephemeral`。若 stdin 被管道且同时给了 prompt 参数，Codex 把 prompt 当作指令、管道内容当作附加上下文：

```bash
curl -s https://jsonplaceholder.typicode.com/comments \
  | codex exec "format the top 20 items into a markdown table" \
  > table.md
```

### 权限与安全

默认 `codex exec` 跑只读沙箱。自动化里按最小权限给：

- 允许编辑：`codex exec --sandbox workspace-write "<task>"`
- 更宽访问：`codex exec --sandbox danger-full-access "<task>"`（仅在受控环境，例如隔离的 CI runner 或容器里使用）

`--full-auto` 已不再支持，改用 `--sandbox workspace-write`，或用 `--approve-for-me` 把审批请求走自动评审 + workspace-write 沙箱。

`--ignore-user-config` 不加载 `$CODEX_HOME/config.toml`；`--ignore-rules` 跳过用户与项目级 execpolicy `.rules` 文件，用于受控自动化。若启用了 `required = true` 的 MCP server 初始化失败，`codex exec` 直接报错退出而不是缺着该 server 继续跑。

### 机器可读输出

加 `--json` 后 `stdout` 变成 JSON Lines 流，逐行是 `thread.started`、`turn.started`、`turn.completed`、`turn.failed`、`item.*`、`error` 等事件；item 类型含 agent 消息、推理、命令执行、文件变更、MCP 工具调用、Web 搜索、计划更新。

```bash
codex exec --json "summarize the repo structure" | jq
```

样例流：

```jsonl
{"type":"thread.started","thread_id":"0199a213-81c0-7800-8aa1-bbab2a035a53"}
{"type":"turn.started"}
{"type":"item.started","item":{"id":"item_1","type":"command_execution","command":"bash -lc ls","status":"in_progress"}}
{"type":"item.completed","item":{"id":"item_3","type":"agent_message","text":"Repo contains docs, sdk, and examples directories."}}
{"type":"turn.completed","usage":{"input_tokens":24763,"cached_input_tokens":24448,"output_tokens":122,"reasoning_output_tokens":0}}
```

只要最终消息时用 `-o <path>` / `--output-last-message <path>` 写入文件，同时仍打印到 `stdout`。

### 结构化输出

需要下游稳定字段时用 `--output-schema` 传 JSON Schema：

```json
{
  "type": "object",
  "properties": {
    "project_name": { "type": "string" },
    "programming_languages": {
      "type": "array",
      "items": { "type": "string" }
    }
  },
  "required": ["project_name", "programming_languages"],
  "additionalProperties": false
}
```

```bash
codex exec "Extract project metadata" \
  --output-schema ./schema.json \
  -o ./project-metadata.json
```

最终输出形如：

```json
{
  "project_name": "Codex CLI",
  "programming_languages": ["Rust", "TypeScript", "Shell"]
}
```

### 自动化中的认证

默认复用已保存的 CLI 凭据。在 GitHub Actions 里优先使用官方 Action（见下一节），由 Action 安装 Codex、起 Responses API 代理、按可配安全策略跑 Codex，从而降低 API key 暴露面。

**不要**在 checkout 或运行仓库受控代码的 workflow 里把 `OPENAI_API_KEY` 或 `CODEX_API_KEY` 设为 job 级环境变量——同 job 里的构建脚本、测试、依赖生命周期 hook 或被攻破的 action 都能读到。其他自动化环境里，仅在真正需要的那次调用前内联设置 `CODEX_API_KEY`，并确保同进程环境里没有不可信代码：

```bash
CODEX_API_KEY=<api-key> codex exec --json "triage open bug reports"
```

`CODEX_API_KEY` 可与 `codex exec`、`codex review`、TypeScript SDK、`codex exec-server --remote` 配合使用。原文另有一个折叠小节「在 CI/CD 用 ChatGPT 托管认证（高级）」说明：API key 仍是自动化默认；只有确实需要以 Codex 用户身份跑时才走该路径，并把 `~/.codex/auth.json` 当密码对待，不要提交、不要贴工单、不要群里分享。公共 / 开源仓库不要用此路径。

### 续跑与 Git 仓库要求

两段式流水线续跑：

```bash
codex exec "review the change for race conditions"
codex exec resume --last "fix the race conditions you found"
```

也可 `codex exec resume <SESSION_ID>` 指定会话。Codex 要求命令在 Git 仓库内运行以防破坏性改动；确信环境安全时用 `codex exec --skip-git-repo-check` 跳过。

### 常见自动化模式：CI 失败自动修

GitHub Actions 里用 `openai/codex-action`，不要自己装 CLI 再把 API key 传给 shell step。典型模式：主 CI 失败后触发后续 workflow；以只读权限 checkout 失败 commit；在 Codex 之前跑 setup 但不暴露 key；跑 Codex Action；把本地变更序列化成 patch artifact；在另一个 job 应用 patch 并开 PR。Codex job 只给 `contents: read`，`open_pr` job 才有 `contents: write` 与 `pull-requests: write` 但拿不到 `OPENAI_API_KEY`。完整 YAML 见原文存档（约 110 行，含 `workflow_run` 触发、`actions/checkout@v5`、`actions/setup-node@v4`、`openai/codex-action@v1`、`actions/upload-artifact@v4`、`actions/download-artifact@v4`、`gh pr create` 等步骤）。

### 高级 stdin 管道

- **prompt + stdin**：指令自己写好，把命令输出作为上下文管道进来。例如 `npm test 2>&1 | codex exec "summarize the failing tests and propose the smallest likely fix" | tee test-summary.md`；类似地可用于日志摘要、TLS/HTTP 排障、Slack 简报、PR 评论草稿。
- **`codex exec -`**：stdin 本身就是完整 prompt。适合 prompt 存文件、shell 拼装 prompt、把实时命令输出与指令合并后整体喂给 Codex：
  ```bash
  cat prompt.txt | codex exec -
  generate_prompt.sh | codex exec - --json > result.jsonl
  ```

## GitHub Action

原文存档：[source/github-action.md](source/github-action.md)

`openai/codex-action@v1` 在 CI/CD 里跑 Codex、应用 patch、或从 workflow 文件发评审。Action 会装 Codex CLI、在你提供 API key 时启动 Responses API 代理，并按你指定的权限跑 `codex exec`。

### 前置条件

- 把 OpenAI key 存为 GitHub secret（例如 `OPENAI_API_KEY`）并在 workflow 中引用。
- job 跑在 Linux 或 macOS runner 上；Windows 必须设 `safety-strategy: unsafe`。
- 调用前先 checkout 代码，让 Codex 能读仓库内容。
- 决定跑哪些 prompt：inline 用 `prompt`，仓库里的 Markdown / 文本文件用 `prompt-file`。

### 示例 workflow

下面的 workflow 在新 PR 上评审、把 Codex 响应回贴到 PR：

```yaml
name: Codex pull request review
on:
  pull_request:
    types: [opened, synchronize, reopened]

jobs:
  codex:
    runs-on: ubuntu-latest
    permissions:
      contents: read
    outputs:
      final_message: ${{ steps.run_codex.outputs.final-message }}
    steps:
      - uses: actions/checkout@v5
        with:
          ref: refs/pull/${{ github.event.pull_request.number }}/merge
          fetch-depth: 0
          persist-credentials: false

      - name: Run Codex
        id: run_codex
        uses: openai/codex-action@v1
        with:
          openai-api-key: ${{ secrets.OPENAI_API_KEY }}
          prompt-file: .github/codex/prompts/review.md
          output-file: codex-output.md

  post_feedback:
    runs-on: ubuntu-latest
    needs: codex
    if: needs.codex.outputs.final_message != ''
    permissions:
      issues: write
      pull-requests: write
    steps:
      - name: Post Codex feedback
        uses: actions/github-script@v7
        with:
          github-token: ${{ github.token }}
          script: |
            await github.rest.issues.createComment({
              owner: context.repo.owner,
              repo: context.repo.repo,
              issue_number: context.payload.pull_request.number,
              body: process.env.CODEX_FINAL_MESSAGE,
            });
        env:
          CODEX_FINAL_MESSAGE: ${{ needs.codex.outputs.final_message }}
```

### 输入项

- `prompt` / `prompt-file`（二选一）：inline 指令或仓库内 Markdown / 文本路径；建议放 `.github/codex/prompts/`。
- `codex-args`：额外 CLI flag，JSON 数组（如 `["--ephemeral"]`）或 shell 字符串（如 `--profile ci`）。
- `model`、`effort`：选 agent 配置，留空走默认。
- `sandbox`：与运行时所需权限匹配，可选 `workspace-write`、`read-only`、`danger-full-access`。
- `output-file`：把最终消息落盘，供后续 step 上传或 diff。
- `codex-version`：固定 CLI 版本，留空用最新发布。
- `codex-home`：跨 step 复用配置与 MCP 设置时指向共享 Codex home。

### 权限收敛

- `safety-strategy`（默认 `drop-sudo`）：跑 Codex 前移除 `sudo`，对该 job 不可逆，保护内存中的 secret；Windows 必须设 `unsafe`。
- `unprivileged-user`：与 `safety-strategy: unprivileged-user` 及 `codex-user` 配合以指定账户跑 Codex，确保该用户对 checkout 有读写权限。
- `read-only`：禁止 Codex 改文件与联网，但仍以提权身份运行——不要单独靠它保 secret。
- `sandbox`：在 Codex 内部限制文件系统与网络，选最窄仍能完成任务的档位。
- `allow-users`、`allow-bots`：限制谁能触发 workflow；默认仅 write 权限用户可跑，额外受信账户显式列出，留空即默认行为。

### 输出与安全清单

Action 通过 `final-message` 输出最后一条 Codex 消息，可映射为 job output 或在后续 step 直接处理；`output-file` 配合 artifact 收集完整 transcript；需要结构化数据时通过 `codex-args` 透 `--output-schema`。

安全清单：限制谁能起 workflow（优先受信事件或显式审批）；对 PR 标题 / commit message / issue body 做 prompt 注入清洗（HTML 注释、隐藏文本先审）；`OPENAI_API_KEY` 用 `drop-sudo` 或非特权用户保护，多租户 runner 上不要留 `unsafe`；Codex 放 job 最后一步；怀疑代理日志或输出泄露 secret 立即轮换。

常见排障：同时给了 `prompt` 与 `prompt-file` 时删一个；代理没写 server info 时确认 `openai-api-key` 提供且有效；`drop-sudo` 后 `sudo` 仍可用说明前序 step 恢复了 sudo 或 runner 不是 Linux/macOS；权限错误在 action 前 grant 写权限（`chmod -R g+rwX "$GITHUB_WORKSPACE"` 或非特权用户模式）；触发被拦时调 `allow-users` / `allow-bots`。

## Hooks

原文存档：[source/hooks.md](source/hooks.md)

Hooks 是 Codex 的扩展框架，让你在 agentic 循环里跑脚本或 MCP 工具，例如：把聊天发到自定义日志 / 分析引擎；扫描团队 prompt 阻止误贴 API key；摘要聊天以沉淀持久记忆；回合停止时跑自定义校验；在特定目录定制 prompt。

运行规则：多个文件里命中的 Hook 都会跑；同一事件多个命中命令 Hook 并发启动，一个不能阻止另一个；非托管 Hook 必须先审阅并信任才会执行。

### 事件时机

| 时机 | Hook |
| --- | --- |
| 回合进行中 | `PreToolUse`、`PermissionRequest`、`PostToolUse`、`PreCompact`、`PostCompact`、`UserPromptSubmit`、`SubagentStop`、`Stop` |
| 打断活跃回合 | `Interrupt`（子代理不触发） |
| 会话或子代理启动 | `SessionStart`、`SubagentStart` |
| 主线程结束 | `SessionEnd`（子代理不触发） |

### Hook 发现位置

Codex 在活跃配置层旁找 `hooks.json` 或 `config.toml` 里的内联 `[hooks]` 表。已装插件也可通过插件 manifest 或默认 `hooks/hooks.json` 携带生命周期配置。四个最常用位置：`~/.codex/hooks.json`、`~/.codex/config.toml`、`<repo>/.codex/hooks.json`、`<repo>/.codex/config.toml`。多源并存时全部加载，高优先级层不会替换低优先级层；同一层同时存在 `hooks.json` 与内联 `[hooks]` 时合并并在启动时告警（建议每层只用一种形式）。项目本地 Hook 仅在项目 `.codex/` 层被信任后加载；不信任的项目仍会加载用户与系统级 Hook。

### 审阅与信任

非托管 Hook 运行前必须审阅并信任确切定义；信任按 Hook 当前 hash 记录，新增 / 变更的 Hook 会被标记待审并跳过直到被信任。CLI 里用 `/hooks` 检视来源、审阅 / 信任 / 禁用单个非托管 Hook；启动时需要审阅会打印提示让你开 `/hooks`。来自系统、MDM、云端或 `requirements.toml` 的托管 Hook 标记为 managed，按策略信任，不能在用户浏览器里禁用。一次性自动化若已在 Codex 外部审过 Hook 源，可加 `--dangerously-bypass-hook-trust` 当次跳过持久信任。

### 配置形态

三层结构：事件（如 `PreToolUse`、`PostToolUse`、`PreCompact`、`SubagentStart`、`Stop`）→ matcher 组 → 一个或多个 handler。`hooks.json` 示例（节选）：

```json
{
  "description": "Optional lifecycle hooks for this workspace.",
  "hooks": {
    "SessionStart": [
      {
        "matcher": "startup|resume",
        "hooks": [
          {
            "type": "command",
            "command": "python3 ~/.codex/hooks/session_start.py",
            "statusMessage": "Loading session notes",
            "additionalContextLimit": 5000
          }
        ]
      }
    ],
    "SessionEnd": [
      {
        "hooks": [
          { "type": "command", "command": "python3 ~/.codex/hooks/session_end.py", "timeout": 3 }
        ]
      }
    ],
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "command": "/usr/bin/python3 \"$(git rev-parse --show-toplevel)/.codex/hooks/pre_tool_use_policy.py\"",
            "statusMessage": "Checking Bash command"
          }
        ]
      }
    ]
  }
}
```

要点：`description` 是可选顶层元数据；`timeout` 单位秒，多数 Hook 默认 `600`，`SessionEnd` 与 `Interrupt` 默认 `1`（上限 `3`）；`statusMessage` 可选；`additionalContextLimit` 控制命令 Hook 在把全文落盘并改为短预览前能发给模型的 `additionalContext` 体量；`commandWindows`（TOML 里 `command_windows` 或 `commandWindows`）是 Windows 专用命令覆盖；`async = true` 让命令 Hook 后台跑；支持 `command` 与 `mcp_tool` handler，`prompt` 与 `agent` 会被解析但跳过；命令以会话 `cwd` 为工作目录；仓库本地 Hook 建议从 git 根解析而不是相对路径 `.codex/hooks/...`。

等价内联 TOML：

```toml
[[hooks.SessionStart]]
matcher = "^compact$"

[[hooks.SessionStart.hooks]]
type = "command"
command = '/usr/bin/python3 "$(git rev-parse --show-toplevel)/.codex/hooks/session_start.py"'
additionalContextLimit = 5000

[[hooks.PreToolUse]]
matcher = "^Bash$"

[[hooks.PreToolUse.hooks]]
type = "command"
command = '/usr/bin/python3 "$(git rev-parse --show-toplevel)/.codex/hooks/pre_tool_use_policy.py"'
timeout = 30
statusMessage = "Checking Bash command"
```

### MCP 工具 Hook

生命周期事件可直接调用已连接 MCP server 上的工具。示例：Codex 写 / 改文件后让 `scanner` server 扫每个 patch：

```json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Write|Edit",
        "hooks": [
          {
            "type": "mcp_tool",
            "server": "scanner",
            "tool": "scan_patch",
            "input": { "patch": "${tool_input.command}" },
            "timeout": 30,
            "statusMessage": "Scanning edited files"
          }
        ]
      }
    ]
  }
}
```

字段：`type` 必须 `mcp_tool`；`server` 为已连接 server 名；`tool` 为该 server 暴露的工具名；`input` 为可选 JSON 参数模板（默认 `{}`）；`timeout` 默认 `600`；`statusMessage` 可选。用 `${field.nested}` 从事件展开字段，整个值被占位符替换时保留 JSON 类型，嵌在字符串里则按文本渲染。MCP Hook 复用既有连接，不新建 / 重连；工具返回阻断决策时可阻断操作，错误、缺 server、工具不可用不阻断；同步执行，不请求工具审批也不触发其他 Hook；`SessionStart` 可能在 MCP server 就绪前跑，此时不阻断会话；`SessionEnd` 不支持 MCP 工具 Hook。

### 关闭 Hook

默认启用。在 `config.toml` 关闭：

```toml
[features]
hooks = false
```

feature key 是 `hooks`（`codex_hooks` 仍是已废弃别名）。管理员可在 `requirements.toml` 用 `[features].hooks = false` 强制关闭。

### 托管 Hook 与插件携带 Hook

企业场景在全局 `requirements.toml` 里配 `mcp_tool` handler；强制托管 Hook 时 `[features].hooks = true`，并用 `allow_managed_hooks_only = true` 忽略用户 / 项目 / 会话 / 插件 Hook 而只加载托管 Hook。`managed_dir`（macOS/Linux）与 `windows_managed_dir`（Windows）指向托管脚本目录，Codex 不分发脚本，由企业 MDM 等另行安装更新；托管命令用该目录下绝对路径。

插件启用时 Codex 可从插件根加载生命周期 Hook（默认 `hooks/hooks.json`，manifest `.codex-plugin/plugin.json` 的 `hooks` 字段可覆盖为 `./` 前缀路径、路径数组、内联对象或内联对象数组）。插件命令接收 `PLUGIN_ROOT`、`PLUGIN_DATA`（兼容期另设 `CLAUDE_PLUGIN_ROOT`、`CLAUDE_PLUGIN_DATA`）。装 / 启插件不会自动信任其 Hook，需在 `/hooks` 里审阅并信任当前定义。

### Matcher 与工具覆盖

`matcher` 是正则串；`"*"`、`""` 或省略即匹配该事件所有出现。不同事件支持的 matcher 维度不同：`PermissionRequest`、`PostToolUse`、`PreToolUse` 按工具名（`Bash`、`apply_patch`（别名 `Edit` / `Write`）、MCP 工具名如 `mcp__filesystem__read_file`）；`PreCompact` / `PostCompact` 按触发源 `manual` / `auto`；`SessionStart` 按启动源 `startup` / `resume` / `clear` / `compact` / `fork`；`SessionEnd` 按结束原因（目前仅 `other`）；`SubagentStart` / `SubagentStop` 按子代理类型；`UserPromptSubmit`、`Stop`、`Interrupt` 不支持 matcher。

`PreToolUse` / `PostToolUse` 可观察的工具路径：Shell 命令（`Bash`）、统一执行 `exec_command`（仍按 `Bash` 匹配，后续 `write_stdin` 轮询可能在原命令结束时补投 `PostToolUse`）、`apply_patch`、MCP 工具、其他本地函数工具（如 `update_plan`、`spawn_agent` 另匹配 `Agent`）；托管工具如 `WebSearch` 不走本地函数工具 Hook 路径。`write_stdin` 是既有 unified-exec 会话的传输，不会为已过 `PreToolUse` 的命令再触发一次。

### 输入 / 输出字段

每个命令 Hook 在 `stdin` 收到一个 JSON 对象。公共字段：`session_id`、`transcript_path`（可空）、`cwd`、`hook_event_name`、`model`（Codex 扩展）。回合级 Hook 另含 `turn_id`。`SessionStart`、`PreToolUse`、`PermissionRequest`、`PostToolUse`、`UserPromptSubmit`、`SubagentStart`、`SubagentStop`、`Stop`、`Interrupt` 还含 `permission_mode`（`default` / `acceptEdits` / `plan` / `dontAsk` / `bypassPermissions`）。`transcript_path` 指向聊天 transcript，但 transcript 格式不是稳定接口。

公共输出字段（`SessionStart`、`PreCompact`、`PostCompact`、`UserPromptSubmit`、`SubagentStop`、`Stop` 支持；`SubagentStart` 接受 `systemMessage` 与 hook 上下文形状但 `continue: false` 不停子代理）：

```json
{
  "continue": true,
  "stopReason": "optional",
  "systemMessage": "optional",
  "suppressOutput": false
}
```

退出 `0` 且无输出视为成功，Codex 继续。`PreToolUse` / `PermissionRequest` 支持 `systemMessage` 但不支持 `continue` / `stopReason` / `suppressOutput`（返回会标记 Hook 失败并继续工具调用）；`PostToolUse` 支持 `systemMessage`、`continue: false`、`stopReason`。

大输出溢出（spilling）：默认每个模型可见 Hook 输出消息约 2500 token，超出部分写到 `<temp_dir>/hook_outputs/<session_id>/<uuid>.txt` 并给模型头尾预览 + 文件路径；写盘失败则仍给截断预览。命令 Hook 用 `additionalContextLimit` 调整阈值（省略走 2500，正整数改阈值，`0` 表示把完整 additionalContext 直接给模型）。因大输出会落盘，Hook 输出不要回传 secret。

### 后台 Hook

默认 Codex 等命令 Hook 跑完才继续触发它的操作；`async = true` 让命令 Hook 后台跑。后台 Hook 与同步 Hook 共用输入、matcher、信任审阅、timeout、大输出处理；`Interrupt` 后台仍 1 秒默认 / 3 秒上限。后台 Hook 结束时在对话下一个安全点交付信息输出：有活跃回合时等当前模型请求与工具调用结束，再把输出给该回合下一个模型请求；无活跃回合时等到下一用户回合（不会自行起新回合）。后台 Hook 不能阻断 / 批准 / 改写触发它的操作；每会话最多 8 个并发后台 Hook，多余排队；会话结束时取消未完成的后台 Hook 并丢弃未交付输出；`SessionEnd` 永远同步跑。

### 各事件契约（速查）

- **`SessionStart`**：matcher 作用于 `source`（`startup` / `resume` / `clear` / `compact` / `fork`）。stdout 纯文本作为额外开发者上下文；JSON 可含 `hookSpecificOutput.additionalContext`。compact 后命中 `source: "compact"` 的 Hook 在下一模型请求前跑，`continue: false` 会结束回合。
- **`SessionEnd`**：主线程在归档 / 删除仍打开的会话、Codex 正常关闭、或会话空闲 30 分钟未被任何客户端打开时跑；子代理不触发。matcher 作用于 `reason`（目前恒 `other`）。同步跑，建议性，输出不引导 Codex 也不延长线程；超时 / 非零退出记为 Hook 失败。
- **`SubagentStart`**：matcher 作用于 `agent_type`。输入含 `turn_id`、`agent_id`、`agent_type`、`permission_mode`。纯文本作为子代理额外上下文；JSON 可给 `additionalContext`；`continue: false` 解析但不停子代理。
- **`PreToolUse`**：可拦截 Bash、`apply_patch` 文件编辑、MCP 工具调用与其他本地函数工具。matcher 作用于 `tool_name`（`apply_patch` 别名 `Edit` / `Write`，但输入里 `tool_name` 仍报 `apply_patch`）。输入含 `turn_id`、`tool_name`、`tool_use_id`、`tool_input`（Bash / apply_patch 用 `tool_input.command`）。纯文本忽略；拒绝返回 `permissionDecision: "deny"` + `permissionDecisionReason`（旧形状 `{"decision":"block","reason":"..."}` 仍接受，退出码 `2` 写 `stderr` 亦可）；不阻断但加可见上下文返回 `additionalContext`；改写调用返回 `permissionDecision: "allow"` + `updatedInput`（Bash / apply_patch 必须含字符串 `command`，其他工具为替换参数对象；只能与 `allow` 合用）。`permissionDecision: "ask"`、旧 `decision: "approve"`、`continue: false`、`stopReason`、`suppressOutput` 解析但未支持。
- **`PermissionRequest`**：Codex 即将请求审批时跑（shell 提权、托管网络审批等；不需要审批的命令不触发）。matcher 作用于 `tool_name`。输入含 `tool_input.description`（若有）。批准返回 `decision.behavior: "allow"`；拒绝返回 `decision.behavior: "deny"` + `decision.message`。多命中时任一 `deny` 胜；都不决策则走正常审批流。不要返回 `updatedInput` / `updatedPermissions` / `interrupt`。
- **`PostToolUse`**：支持工具产出后跑（Bash 即使非零退出也跑）；不能撤销已执行副作用。输入含 `tool_response`。JSON 可含 `systemMessage` 与 `additionalContext`；`decision: "block"` 不撤销已跑命令，而是把工具结果替换为 Hook 反馈并继续模型；`continue: false` 停掉原工具结果的正常处理。退出码 `2` 写 `stderr` 亦可。`updatedMCPToolOutput`、`suppressOutput` 解析但未支持。
- **`PreCompact` / `PostCompact`**：matcher 作用于 `trigger`（`manual` / `auto`）。`PreCompact` 返回 `continue: false` 则不压缩；`PostCompact` 返回 `continue: false` 则压缩后停止。
- **`UserPromptSubmit`**：matcher 不支持。输入含 `prompt`。纯文本作为额外上下文；JSON 可加 `additionalContext`；阻断返回 `decision: "block"` + `reason`（或退出码 `2` + `stderr`）。
- **`SubagentStop`**：matcher 作用于 `agent_type`。输入含 `agent_id`、`agent_type`、`agent_transcript_path`、`stop_hook_active`、`last_assistant_message`。退出 `0` 时期望 JSON；返回 `decision: "block"` + `reason` 让 Codex 在子代理里再跑一轮；任一命中返回 `continue: false` 优先于续跑决策。
- **`Stop`**：matcher 不支持。输入含 `stop_hook_active`、`last_assistant_message`。退出 `0` 时期望 JSON；`decision: "block"` + `reason` 不拒绝回合，而是把 `reason` 当作新用户 prompt 让 Codex 继续；任一命中返回 `continue: false` 优先。
- **`Interrupt`**：主线程打断活跃回合时跑（空闲线程 / 子代理不跑，matcher 忽略）。输入含 `turn_id` 与 `permission_mode`；默认 1 秒超时（可配 1–3 秒）；输出不能阻止打断或重启回合；退出 `0` 无输出或返回含可选 `systemMessage` 的 JSON；纯文本无效。

代码模式（JavaScript 内嵌工具调用）下 Hook 同样生效：`PreToolUse` 可在工具运行前拒绝（promise reject）或用 `updatedInput` 改写输入；`PostToolUse` 的 `block` 不撤销副作用但让 promise 带 Hook reason reject；`PostToolUse` 的 `continue: false` 只换模型可见结果，不 reject 嵌套 promise。
