## MCP（连接外部工具）

原文存档：[source/mcp.md](source/mcp.md)

Model Context Protocol（MCP）让 ChatGPT 和 Codex 使用来自其他系统的工具与信息。一个 MCP server 描述可用的工具并处理其请求——例如查询一张工单或检索文档。

按任务选择路径：

- **建立连接**：用 Plugin Creator 与 Sites 为团队系统创建插件。
- **使用现有 server**：把它连接到 ChatGPT 或 Codex，支持 web、desktop、CLI、IDE 的配置。

> 示例：在团队支持系统中查询工单。

插件把一个 MCP 连接打包，供 ChatGPT 使用；插件也可包含带可复用指令的 skills。若只需要指令，参见站内 /docs/build-plugins。

### 用 Plugin Creator 与 Sites 构建 MCP 插件

用 Plugin Creator 创建并编辑插件，用 Sites 托管其 MCP server。

#### 开始之前

先查看 Plugins 目录（chatgpt.com/plugins）。若需要新连接，准备好系统的 API 文档和经过批准的连接方式；需要时向系统负责人求助。下面的示例创建一个 **Support Ticket Lookup** 插件，把 **[ticketing system]** 替换为你自己的系统名。

<details><summary>使用 ChatGPT Enterprise？</summary>

请工作区 owner 或管理员检查 **Workspace settings → Permissions & roles**：

- **Use plugins**：创建、编辑和使用插件；编辑还需要对该插件的编辑权限。
- **Sites**：创建并发布你的 Site 的访问权限。
- **Upload plugins** 与 **Create plugins with MCPs**：面向发布 MCP 插件的 Site owner。

**Use plugins** 默认开启；两项 MCP 发布权限默认关闭。

</details>

#### 1. 创建插件

新建一个 Work 任务，选择 **@Plugin Creator**，附上你的 API 文档，然后描述任务：

```text
Create a Support Ticket Lookup plugin with an MCP server hosted on Sites, using the attached [ticketing system] API docs. Let me look up a ticket's status, owner, and latest update by ticket number. Make it read-only and tell me what's needed to connect it.
```

还在安排 API 权限？可以先让 Plugin Creator 使用示例数据。

#### 2. 连接你的系统

在同一对话中让 Plugin Creator 把 server 连接到系统 API，并引导你完成登录。使用组织批准的认证方式，不要把密码、API key 等机密放进聊天。

Sites 负责 ChatGPT 与 MCP server 之间的登录；server 仍需有一条经批准的到系统 API 的连接，由它控制可访问的记录与操作。若使用其他宿主，参见站内 developers.openai.com 上的 Build an MCP server 与 Connect and test your plugin 指南。

#### 3. 发布并安装

让 Plugin Creator 用 Sites 发布 server 并给出插件链接，保持当前访问设置。Site owner 必须亲自发布才能创建插件。

1. 打开插件卡片，或在 **Plugins → Personal → Created by you** 下找到它。
2. 依次 **Install**、**Connect**，完成必要登录。

#### 4. 使用插件

新建 Work 任务，用 **@** 选择你的插件，然后用系统里的工单号提问，例如「What's the status of ticket 123?」。在同一对话中可与其他插件的工具一起使用。

### 替换 GPT custom action

GPT custom action 不会自动迁移到插件；应把连接重建为新的 Sites 插件，并尽可能复用现有 API。发布时 Sites 会创建独立插件，不会把连接并入已迁移的插件；两者可在同一对话中使用。Sites 插件暂不支持编辑 skills 或引用文件。

要点：先让原 GPT 写一段重建提示词，把每个操作标注为读/写，附 API 操作、输入、返回字段与回答格式，省略凭证与隐藏指令；再核对原 Actions 设置中的 schema、认证方式与非机密连接配置；最后在 Work 中选 **@Plugin Creator**（Codex 中用 `$plugin-creator`）粘贴提示词并附 schema/API 文档，让它把 server 托管在 Sites 上。

### 故障排查

连接错误或工具缺失时，确认 Site owner 已发布最新版本，且插件已安装并连接；把错误发给 Plugin Creator 或 server owner。ChatGPT 不调用工具时，用 **@** 选中插件并明确要求某次查询。若插件标记为 **Desktop only**，需使用受支持的 desktop app，或请作者调整打包方式——仅有远程 MCP server 并不能让插件兼容 web。

### 连接现有 MCP server

ChatGPT web 通过插件使用远程 MCP 工具；本地 Codex 客户端也可直接连接 MCP server 并共享配置。

ChatGPT desktop app、Codex CLI 与 IDE 扩展共享同一 MCP 配置；配置好 server 后在这些客户端间切换无需重复设置。

#### 支持的 MCP 能力

- **STDIO servers**：作为本地进程运行（由一条命令启动）的 server。
  - 支持环境变量。
- **Streamable HTTP servers**：通过地址访问的 server。
  - Bearer token 认证。
  - OAuth 认证，包括 Client ID Metadata Documents（CIMD）与 Dynamic Client Registration（DCR）。
  - 受信任的一方服务器可用 ChatGPT 会话认证。
- **Server instructions**：Codex 读取初始化时返回的 MCP `instructions` 字段，作为该 server 全部工具的全局性指引。

为 Codex 构建或维护 MCP server 时，把跨工具工作流、约束与限流写进 `instructions`；前 512 字符应自包含，以便 Codex 在决定如何使用该 server 时即可获得最重要的指引。

#### 用 CLI 配置

添加一个 MCP server：

```bash
codex mcp add <server-name> --env VAR1=VALUE1 --env VAR2=VALUE2 -- <stdio server-command>
```

例如添加 Context7（一个用于开发者文档的免费 MCP server）：

```bash
codex mcp add context7 -- npx -y @upstash/context7-mcp
```

其他命令：`codex mcp list` 查看已配置 server；`codex mcp --help` 查看全部命令；对支持 OAuth 的 server 运行 `codex mcp login <server-name>`。在 `codex` TUI 中输入 `/mcp` 查看当前活动的 MCP server。

#### 用 config.toml 配置

更精细的控制可编辑 `~/.codex/config.toml` 或项目级 `.codex/config.toml`（仅受信任项目）。可检索的全部 MCP 选项见 [配置参考](05-配置-高级与参考.md)。每个 server 在配置文件中用一张 `[mcp_servers.<server-name>]` 表配置。

STDIO server 的字段：

- `command`（必填）：启动 server 的命令。
- `args`（可选）：传给 server 的参数。
- `env`（可选）：为 server 设置的环境变量。
- `env_vars`（可选）：允许并转发的环境变量。
- `cwd`（可选）：启动 server 的工作目录。
- `experimental_environment`（可选）：设为 `remote` 时，在可用的远程执行环境中启动该 stdio server。

`env_vars` 可包含纯变量名或带 source 的对象：

```toml
env_vars = ["LOCAL_TOKEN", { name = "REMOTE_TOKEN", source = "remote" }]
```

字符串项与 `source = "local"` 从 Codex 本地环境读取；`source = "remote"` 从远程执行环境读取，需要远程 MCP stdio。

Streamable HTTP server 的字段：

- `url`（必填）：server 地址。
- `auth`（可选）：在已配置 bearer token 与 authorization 头之后再尝试的认证。`oauth`（默认）使用已存储的 MCP OAuth 凭证；`chatgpt` 对受信任的一方 ChatGPT 来源使用当前会话，并以已存储 OAuth 兜底。
- `bearer_token_env_var`（可选）：放入 `Authorization` 的 bearer token 所在环境变量名。
- `http_headers`（可选）：头名到静态值的映射。
- `env_http_headers`（可选）：头名到环境变量名的映射（值从环境取）。
- `http_headers_helper`（可选）：打印 JSON 头对象的本地命令，如 `{"X-Auth": "temporary-token"}`。仅支持本地环境发起的 HTTP MCP 连接，不用于 stdio server 或远程执行环境连接。

其他常用选项：

- `startup_timeout_sec`（可选）：server 启动超时（秒），默认 `10`。
- `tool_timeout_sec`（可选）：server 执行一次工具的超时（秒），默认 `60`。
- `enabled`（可选）：设 `false` 可禁用而不删除 server。
- `required`（可选）：设 `true` 时，该已启用 server 初始化失败会使启动失败。
- `enabled_tools`（可选）：工具白名单。
- `disabled_tools`（可选）：工具黑名单（在 `enabled_tools` 之后应用）。
- `default_tools_approval_mode`（可选）：该 server 工具的默认审批行为，取值 `auto`、`prompt`、`writes`、`approve`；`writes` 会对未标记只读的工具提示确认。
- `tools.<tool>.approval_mode`（可选）：单个工具的审批行为覆盖。
- `tools.<tool>.output_token_limit`（可选）：单个工具输出的 token 预算。

顶层 `mcp_optional_startup_grace_ms` 控制 Codex 在构建初始工具目录时等待可选 MCP server 的时长，默认 `1000` 毫秒；设 `0` 则等待每个 server 自己的 `startup_timeout_sec`。必需 server 仍使用其启动超时。

OAuth 客户端注册与回调：当授权服务器要求预注册客户端时，添加 server 时给出 client ID：

```bash
codex mcp add example --url https://mcp.example.com --oauth-client-id my-client
```

机密客户端再传 `--oauth-client-secret`，从环境变量读取：

```bash
codex mcp add example --url https://mcp.example.com --oauth-client-id my-client --oauth-client-secret "$MCP_CLIENT_SECRET"
```

Codex 会显示需要在服务商处注册的完整回调 URL：

```text
OAuth callback URL: http://127.0.0.1/callback
```

并把回调与 client ID 一并存入 `config.toml`：

```toml
[mcp_servers.example]
url = "https://mcp.example.com"

[mcp_servers.example.oauth]
client_id = "my-client"
callback_url = "http://127.0.0.1/callback"
```

回调选择规则（依 OAuth 配置与授权服务器元数据而定）：

| OAuth 配置 | Issuer 支持 | 使用的回调 |
| --- | --- | --- |
| `callback_url` 无 `client_id` | 支持 | 使用配置回调进行客户端注册。 |
| `callback_url` 无 `client_id` | 不支持 | 使用配置回调，并追加 server 专属回调 ID。 |
| `client_id` 与 `callback_url` | 支持 | 复用配置回调；授权响应须含匹配的 `iss`。 |
| `client_id` 且 `callback_url` 以正确回调 ID 结尾 | 不支持 | 原样复用配置回调。 |
| `client_id` 且 `callback_url` 缺正确回调 ID | 不支持 | 忽略配置回调；用 `mcp_oauth_callback_url` 或默认 `http://127.0.0.1/callback` 并追加回调 ID。 |
| `client_id` 无配置 `callback_url` | 支持或不支持 | 使用全局或默认回调，并追加 server 专属回调 ID。 |

可用 `mcp_oauth_callback_url` 自定义回调路径或远程 ingress 地址；用 `mcp_oauth_callback_port` 选固定全局监听端口，或用 `mcp_servers.<server-name>.oauth.callback_port` 覆盖单个 server。对 `http://127.0.0.1` 这类无显式端口的回调，Codex 在显示与存储时省略监听端口，授权时再插入当前端口。返回的 `iss` 不匹配一律拒绝交换授权码。用 `mcp_servers.<server-name>.scopes` 选择 OAuth 作用域，单次登录可 `codex mcp login <name> --scopes read,write` 覆盖。

config.toml 示例：

```toml
[mcp_servers.context7]
command = "npx"
args = ["-y", "@upstash/context7-mcp"]
env_vars = ["LOCAL_TOKEN"]

[mcp_servers.context7.env]
MY_ENV_VAR = "MY_ENV_VALUE"
```

```toml
# Optional MCP OAuth callback overrides (used by `codex mcp login`)
mcp_oauth_callback_port = 5555
mcp_oauth_callback_url = "https://devbox.example.internal/callback"
```

```toml
[mcp_servers.figma]
url = "https://mcp.figma.com/mcp"
bearer_token_env_var = "FIGMA_OAUTH_TOKEN"
http_headers = { "X-Figma-Region" = "us-east-1" }
```

```toml
[mcp_servers.chrome_devtools]
url = "http://localhost:3000/mcp"
enabled_tools = ["open", "screenshot"]
disabled_tools = ["screenshot"] # applied after enabled_tools
default_tools_approval_mode = "prompt"
startup_timeout_sec = 20
tool_timeout_sec = 45
enabled = true

[mcp_servers.chrome_devtools.tools.open]
approval_mode = "approve"
output_token_limit = 30000
```

#### 插件提供的 MCP server

已安装插件可在其 manifest 中打包 MCP server；这些 server 由插件启动，用户配置不设置其传输命令，但仍可在 `plugins.<plugin>.mcp_servers.<server>` 下控制开关与工具策略：

```toml
[plugins."sample@test".mcp_servers.sample]
enabled = true
default_tools_approval_mode = "prompt"
enabled_tools = ["read", "search"]

[plugins."sample@test".mcp_servers.sample.tools.search]
approval_mode = "approve"
```

插件提供的 HTTP MCP server 也可在 `.mcp.json` 中声明 OAuth 设置（manifest 用 camelCase 字段 `clientId`、`callbackUrl`、`callbackPort`）：

```json
{
  "mcpServers": {
    "sample": {
      "type": "http",
      "url": "https://mcp.example.com/mcp",
      "oauth": {
        "clientId": "my-pre-registered-client",
        "callbackUrl": "http://127.0.0.1/callback/registered"
      }
    }
  }
}
```

#### 常用 MCP server 举例

- OpenAI Docs MCP：检索并阅读 OpenAI 开发者文档。
- Context7：接入最新的开发者文档。
- Figma Local / Remote：访问你的 Figma 设计。
- Playwright：用 Playwright 控制并检查浏览器。
- Chrome Developer Tools：控制并检查 Chrome。
- Sentry：访问 Sentry 日志。
- GitHub：管理 `git` 之外的 GitHub 资源（如 pull request 与 issue）。

## 技能与插件

原文存档：[source/skills-and-plugins.md](source/skills-and-plugins.md)

技能与插件帮助 ChatGPT 和 Codex 用恰当的指令、资源与工具完成重复性工作，避免在每次对话里重复粘贴相同的提示词、模板、需求或流程。

- **skill**：为特定任务或工作流打包的指令与配套资源。
- **plugin**：可安装的打包体，可包含 skills 与 MCP server；MCP server 暴露工具，还可附带自定义 ChatGPT UI。插件也可为 Codex 运行时（含 ChatGPT Work 与 Codex）附带 lifecycle hooks。

### 用技能处理重复工作

skill 是可复用的工作流，为 ChatGPT 或 Codex 提供任务专属指引，把你既有的重复做法固化下来，使产品每次遇到同类任务都按同一流程执行。一个 skill 可组合：

- 名称与描述，帮助 ChatGPT/Codex 识别何时适用；
- 定义流程与预期结果的工作流指令；
- 配套资源，如模板、示例、品牌规范、schema 或已连接工具。

当好结果依赖可重复的方法时，技能最有价值：每日简报、文档评审、做演示、套用团队写作规范，或每周从相同已连接工具收集信息。ChatGPT 与 Codex 可在请求匹配其用途时自动选用 skill，你也可显式选择。ChatGPT 用 `@` 提及，Codex 用 `$` 提及 skills。

### 构建技能

从一个你已在重复的任务开始，把它做成聚焦的 playbook。步骤：

1. **选一个聚焦任务**：记下你通常从什么开始（文件、链接、笔记），以及完成结果应是什么样。
2. **描述工作流**：ChatGPT 中以 `@skill-creator` 开头，Codex 中用 `$skill-creator`；说明目标、步骤、预期格式，以及应始终包含或避免的内容，有模板或好例子就附上。
3. **评审并试跑草稿**：检查指令，用真实请求测试，结果漏步或偏离格式时打磨。
4. **安装并复用**：启用后，ChatGPT/Codex 可在相关请求中使用，或由你显式选择；工作区允许时还可分享给同事。

更详细的构建方法见站内 /docs/build-skills 指南。

### 用插件获得工具与共享工作流

插件让可复用能力更易安装与分享，可把 skills 与 MCP server 组合，接入 GitHub、Google Drive、Slack 等服务的工具与上下文。ChatGPT 与 Codex 共用一个统一插件目录；安装后直接描述任务，或用你所在端的调用语法显式选择插件或其中的 skill。安装与使用插件见站内 /docs/plugins。

### 在 skill 与 plugin 之间选择

需要聚焦任务的可复用指令时用 skill；想要一个可安装包、能把指令与已连接服务或其他工具组合时用 plugin。通过对话在 ChatGPT 中构建插件见 /docs/build-plugins；迁移既有自定义 GPT 工作流见 /docs/migrate-custom-gpts。你也可用 Record & Replay 演示工作流，录制会被转成可复用 skill。若插件需要连接服务或暴露 MCP 工具，见 developers.openai.com 上的 Build an MCP server；准备好公开评审时见 Submit plugins。

## 代码审查

原文存档：[source/code-review.md](source/code-review.md)

用 ChatGPT 或 Codex 理解代码改动、排查潜在问题并准备评审反馈。

### Pull request 审查

Code Review 插件展示一个 pull request 的描述、改动文件、评论与检查结果，可在批准前排查潜在问题。GitHub 代码审查已正式可用；GitLab merge request 支持处于预览阶段。要从 GitLab 用 `@codex review` 触发云端审查或自动 merge request 审查，见站内 /docs/third-party/gitlab。仓库触发的审查见 /docs/third-party/github。

查看一个 pull request：

1. 从侧边栏打开 **Code Review**。
2. 按提示连接你的来源账号，使用有权访问该仓库的账号。
3. 从侧边栏选择一个 pull request，或在搜索框输入其链接。
4. 在 **Summary** 阅读描述、动态、评论与检查；打开 **Changes** 对照 diff 查看改动文件与评论。

可在个人收件箱中按 **Assigned to me**、**Assigned to my team**、**Authored by me** 过滤需要你关注的审查；用 **Mark as viewed** 标记已查看文件；跨多个相互依赖的 pull request 用 **Stack** 查看关联 PR 的 diff、评论与检查。

启用自动审查后，Codex 可在你打开之前审查 GitHub pull request，评论出现在 GitHub 与 Code Review 中；云端审查无需你创建或管理云环境。在 PR 对话中，描述预期行为并请 Codex 解释或排查改动。例如一个 issue 看板新增 **Open**/​**Closed** 过滤器时：

```text
Walk me through this pull request. Focus on the default filter and what
happens when there are no matching issues. All should remain the default.
```

索取证据：

```text
Show me the code path and tests for the no-matches case. Explain what is
covered and what still needs verification.
```

可用 **Review instructions** 设定跨仓库的审查准则与报告格式，例如：

```text
Start with a short summary. Prioritize behavior changes, data loss, and
missing edge-case tests. For each finding, explain the triggering input,
expected behavior, and actual behavior. Use our team's concise review style.
```

在对话中评审 pull request 不会自动发评论、批准或合并；由你选择哪些发现要分享。核实后可让 Codex 起草评审评论：

```text
Using the team review guidelines we discussed, draft a comment describing
the no-matches behavior we verified, what should happen instead, and the test
that would cover it. Keep the comment as a draft.
```

检查草稿的文件与行号引用后再发布；用 **Submit review** 选择 **Comment**、**Approve** 或 **Request changes** 发送到来源方。

### 审查本地改动

Codex 内置的 `/review` 命令审查 Git checkout 中的改动，与处理 pull request 的 Code Review 插件互补。

在 CLI 中输入 `/review` 打开审查预设；Codex 启动一个专门的 reviewer，读取所选 diff 并按优先级报告可执行的发现，不会改动你的工作区。可选范围：

- **Review against a base branch**：找到 merge base 并审查你分支的 diff。
- **Review uncommitted changes**：包含已暂存、未暂存与未跟踪文件。
- **Review a commit**：审查所选 commit 的确切变更集。
- **Custom review instructions**：按你给出的准则聚焦审查。

CLI 中审查结果作为转录中的一轮出现；想让审查使用与当前会话不同的模型，在 `config.toml` 中设置 `review_model`。若让 Codex 应用它发现的修复，你常规的沙箱与审批设置仍然适用。

## 图片输入（codex --image）

原文存档：[source/image-inputs.md](source/image-inputs.md)

当任务依赖视觉上下文时——如错误截图、界面设计、架构图或既有素材——在提示中加入图片。说明要 ChatGPT 查看什么、期望什么结果，不要只靠图片本身传达任务。

在 CLI 中，可把图片粘贴进交互式 composer，或在命令行传入一个或多个文件：

```bash
codex -i screenshot.png "Explain this error and suggest the smallest fix"
codex --image before.png,after.png "Compare these states and list the regressions"
```

多张图片用逗号分隔路径，或重复 `--image`。Codex 接受常见图片格式，包括 PNG 与 JPEG。

围绕图片写提示：说明图片内容、指出关键区域、写明输出与约束；多张图片时逐一标识并说明如何比较。例如：

```text
Compare this checkout screen with the design. Fix spacing and typography only;
do not change behavior. Verify the result with a new screenshot.
```

要 ChatGPT 检查视觉参考时用图片输入；要它创建或编辑图片时改用图片生成功能（站内 /docs/image-generation）。

## 网络搜索（codex --search）

原文存档：[source/web-search.md](source/web-search.md)

ChatGPT 自带一方网络搜索工具。把所有网页结果视为不可信输入。

在 CLI 中，传 `--search` 可为单次运行抓取实时结果：

```bash
codex --search "Summarize the latest release notes for this dependency"
```

搜索在交互式转录中显示为 `web_search` 条目，也出现在 `codex exec --json` 输出中。

### 配置本地网络搜索

对本地 Codex 对话，默认启用缓存搜索。缓存模式使用 OpenAI 维护的索引，而非实时抓取任意页面，可降低但不能消除提示注入风险。网络搜索是托管工具，独立于沙箱本地命令联网；它不使用权限配置中的网络代理或域名白名单，在命令联网被禁用时仍可可用。用 `web_search`、`tools.web_search.allowed_domains` 以及受管的 `allowed_web_search_modes` 按需配置；搜索域名过滤不限制本地命令流量、应用、连接器或 MCP server。

任务依赖最新信息时用实时搜索：在 `config.toml` 设 `web_search = "live"`；设 `web_search = "disabled"` 关闭该工具；`"indexed"` 模式仅在搜索索引把关请求时才允许外部访问。Codex 以完全访问运行时，网络搜索默认为实时结果。配置文件位置与优先级见 [配置基础](04-配置-基础与示例.md)。

### 自定义模型提供方的搜索

自定义模型提供方若支持兼容的搜索端点，可选择启用独立网络搜索：

```toml
model_provider = "custom"
web_search = "live"

[model_providers.custom]
name = "Custom Responses provider"
base_url = "https://example.com/v1"
env_key = "CUSTOM_RESPONSES_API_KEY"
supports_standalone_web_search = true
```

自定义提供方默认 `supports_standalone_web_search = false`。独立网络搜索仍在开发中，默认关闭；开启该提供方能力并不等于启用功能——提供方、所选模型与运行时都须支持独立搜索，且工作区与受管搜索限制仍然适用。
