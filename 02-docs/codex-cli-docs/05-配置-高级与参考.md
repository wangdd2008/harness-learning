## 高级配置

原文存档：[source/config-advanced.md](source/config-advanced.md)

当你需要对模型提供商、策略与集成做更精细的控制时，使用本页介绍的高级选项。基础快速上手见 [配置：基础与示例](04-配置-基础与示例.md)；项目指引、可复用能力、自定义斜杠命令、子代理工作流与集成的背景见 Customization（站内路径 /docs/customization/overview）；全部配置键见本页「配置参考」。

### 将这些示例应用于「本地计算机访问 + Work Cloud」

下列示例描述的是 Codex 本机配置。在为「本地计算机访问 + Work Cloud」改造它们之前，请先查阅配置参考。

- **策略范围**：对于带本地访问与 dots 的 Work，当启用受管策略时，受支持的 Global 策略管辖共享云编排器；适用的本地执行要求管辖所连接的计算机。Work 云容器保留既有 Work Cloud 策略。
- **本地执行**：MDM 与旧版受管设备要求的优先级高于 Agent Security；设备系统要求文件的优先级低于 Agent Security。
- **企业 hooks**：若为你的工作区启用，该特性支持管理员定义的 MCP hooks，在云协调器（编排器）上针对受支持的生命周期与工具事件运行。即使工具在本地执行，命令 hooks 以及来自本地配置或插件的 hooks 在云编排下也不受支持。
- **审计**：在依赖这些 hooks 之前，先测试回调连接、确认它收到的事件、并检查失败如何影响任务。MCP hooks 并不提供完整的 Compliance API 审计轨迹。
- **其他设置**：自定义模型提供商与主机本地路径不会通过受管配置带入此特性。请在 Managed configuration（站内路径 /docs/enterprise/managed-configuration）中查阅网络限制与字段级合并规则。

hooks 的支持范围与配置指引见 Hooks（站内路径 /docs/hooks）。

### Profiles（命名配置层）

Profile 让你保存命名的配置层并从 CLI 切换。传入 `--profile profile-name` 时，Codex 先加载 `~/.codex/config.toml`，再叠加 `~/.codex/profile-name.config.toml`。Profile 名可含字母、数字、连字符与下划线。

每个 Profile 单独建一个 TOML 文件，在其中使用顶层配置键，不要嵌套在 `[profiles.profile-name]` 之下。下例使用 GPT-6.1 Sol，需要你的登录账号或工作区有访问权限；若不可用，改选你可用的模型。

```toml
# ~/.codex/deep-review.config.toml
model = "gpt-6.1-sol"
model_reasoning_effort = "medium"
approval_policy = "on-request"
model_catalog_json = "/Users/me/.codex/model-catalogs/deep-review.json"
```

```shell
codex --profile deep-review
codex exec --profile deep-review "review this change"
```

Profile 文件位于基础用户配置之上、项目与 CLI 配置之下，因此只需写与基础配置不同的值。Profile 文件也可覆盖 `model_catalog_json`，两个文件都设置时以 Profile 值为准。

在 Codex 0.134.0 及之后，`--profile` 不再读取 `config.toml` 中的 `[profiles.profile-name]`，顶层 `profile = "profile-name"` 选择器也不再支持。请把旧的 Profile 设置迁移到 `~/.codex/profile-name.config.toml`，再从 `config.toml` 删除对应的 `[profiles.profile-name]` 表与 `profile = "profile-name"` 选择器。

### 从 CLI 做一次性覆盖

除了编辑 `~/.codex/config.toml`，也可在单次运行中从 CLI 覆盖配置：

- 有专用 flag 时优先用 flag（例如 `--model`）。
- 需要覆盖任意键时用 `-c` / `--config`。

下列模型覆盖同样需要 GPT-6.1 Sol 访问权限；没有则替换为你可用的模型：

```bash
# 专用 flag
codex --model gpt-6.1-sol
# 通用键值覆盖（值是 TOML，不是 JSON）
codex --config model='"gpt-6.1-sol"'
codex --config sandbox_workspace_write.network_access=true
codex --config 'shell_environment_policy.include_only=["PATH","HOME"]'
```

说明：

- 键可用点号记法设置嵌套值（例如 `mcp_servers.context7.enabled=false`）。
- `--config` 的值按 TOML 解析；不确定时给值加引号，避免 shell 按空格切分。
- 若值无法按 TOML 解析，Codex 把它当作字符串。

### 配置与状态位置

Codex 把本地状态存放在 `CODEX_HOME` 下（默认 `~/.codex`）。常见文件：

- `config.toml`（你的本地配置）
- `auth.json`（若使用基于文件的凭据存储）或系统 keychain/keyring
- `history.jsonl`（若启用历史持久化）
- 其他每用户状态，如日志与缓存

认证细节（含凭据存储模式）见 Authentication（站内路径 /docs/auth）；完整配置键清单见本页「配置参考」。提交到仓库或系统路径的共享默认值、规则与 skills 见 Team Config（站内路径 /docs/enterprise/admin-setup）。

若只需把内置 OpenAI 提供商指向某个 LLM 代理、路由器或开启数据驻留的项目，直接在 `config.toml` 设 `openai_base_url`，而不必新建提供商条目。这会改变内置 `openai` 提供商的 base URL，无需单独的 `model_providers.<id>` 条目。

```toml
openai_base_url = "https://us.api.openai.com/v1"
```

### 项目配置文件（`.codex/config.toml`）

除用户配置外，Codex 还会读取仓库内 `.codex/config.toml` 中的项目级覆盖。Codex 从项目根走到当前工作目录，加载沿途每个 `.codex/config.toml`；多个文件定义同一键时，离工作目录最近者胜出。

出于安全，Codex 仅在项目受信任时加载项目级配置。项目不受信任时，Codex 忽略项目 `.codex/` 各层，包括 `.codex/config.toml`、项目本地 hooks 与项目本地规则；用户层与系统层仍独立加载。

项目配置内的相对路径（例如 `model_instructions_file`）相对包含该 `config.toml` 的 `.codex/` 目录解析。

项目配置不能覆盖那些会重定向凭据、改动主机归属的应用请求元数据、更改提供商认证、选择配置 Profile、或运行机器本地通知/遥测命令的设置。Codex 在项目本地 `.codex/config.toml` 中忽略以下键并在启动时打印警告：`openai_base_url`、`chatgpt_base_url`、`apps_mcp_product_sku`、`model_provider`、`model_providers`、`notify`、`profile`、`profiles`、`experimental_realtime_ws_base_url`、`otel`。提供商、通知与遥测键请放在用户级 `~/.codex/config.toml`；用 `--profile profile-name` 配合 `~/.codex/profile-name.config.toml` 选择 Profile。

### Hooks

Codex 还可从 `hooks.json` 文件或紧邻活动配置层的 `config.toml` 内联 `[hooks]` 表加载生命周期 hooks。最常用的四个位置：

- `~/.codex/hooks.json`
- `~/.codex/config.toml`
- `<repo>/.codex/hooks.json`
- `<repo>/.codex/config.toml`

项目本地 hooks 仅在项目 `.codex/` 层受信任时加载；用户级 hooks 不受项目信任影响。内联 TOML hooks 与 `hooks.json` 使用相同事件结构：

```toml
[[hooks.PreToolUse]]
matcher = "^Bash$"

[[hooks.PreToolUse.hooks]]
type = "command"
command = '/usr/bin/python3 "$(git rev-parse --show-toplevel)/.codex/hooks/pre_tool_use_policy.py"'
timeout = 30
statusMessage = "Checking Bash command"
```

若同一层同时含 `hooks.json` 与内联 `[hooks]`，Codex 两者都加载并告警。每层优先只用一种表示。当前事件清单、输入字段、输出行为与限制见 Hooks（站内路径 /docs/hooks）。

### 项目根检测

Codex 通过从工作目录向上走直到项目根，来发现项目配置（如 `.codex/` 各层与 `AGENTS.md`）。默认把含 `.git` 的目录视为项目根。可在 `config.toml` 设 `project_root_markers` 自定义：

```toml
# 当目录含以下任一标记时视为项目根。
project_root_markers = [".git", ".hg", ".sl"]
```

设 `project_root_markers = []` 可跳过向上搜索，把当前工作目录视为项目根。

### 自定义模型提供商

若你的组织提供模型网关，客户端配置与验证见 Connect to a gateway（站内路径 /docs/enterprise/connect-to-a-gateway）；组织范围部署见 Roll out a gateway（站内路径 /docs/enterprise/roll-out-a-gateway）。

模型提供商定义 Codex 如何连接模型（base URL、线上 API、认证、可选 HTTP 头）。自定义提供商不能占用保留的内置提供商 ID：`openai`、`ollama`、`lmstudio`。

定义更多提供商并把 `model_provider` 指向它们：

```toml
model = "gpt-6.1-sol"
model_provider = "proxy"
[model_providers.proxy]
name = "OpenAI using LLM proxy"
base_url = "http://proxy.example.com"
env_key = "OPENAI_API_KEY"
[model_providers.local_ollama]
name = "Ollama"
base_url = "http://localhost:11434/v1"
[model_providers.mistral]
name = "Mistral"
base_url = "https://api.mistral.ai/v1"
env_key = "MISTRAL_API_KEY"
```

若自定义提供商支持独立 web 搜索端点，在其配置中声明该能力：

```toml
[model_providers.proxy]
name = "OpenAI using LLM proxy"
base_url = "https://proxy.example.com/v1"
env_key = "OPENAI_API_KEY"
supports_standalone_web_search = true
```

该设置对自定义提供商默认 `false`。独立 web 搜索仍在开发中、默认关闭。把提供商能力设为 `true` 并不会真的启用它：提供商必须支持兼容端点，且所选模型与运行时必须支持独立搜索。已配置的 `web_search` 模式与受管搜索限制仍然适用。

按需添加请求头：

```toml
[model_providers.example]
http_headers = { "X-Example-Header" = "example-value" }
env_http_headers = { "X-Example-Features" = "EXAMPLE_FEATURES" }
```

要通过组织身份提供者做浏览器登录，使用 native gateway OAuth（站内路径 /docs/enterprise/connect-to-a-gateway）。用授权与 token URL、公共 client ID 与 token 交付设置配置 `[model_providers.<id>.gateway_oauth]`。它配合 `requires_openai_auth = false` 使用，无需 ChatGPT 登录、PowerShell、Azure CLI 或外部凭据助手；网关必须在配置的 cookie 或自定义头中接受 OAuth token。

当提供商需要 Codex 从外部凭据助手取 bearer token 时，使用命令式认证：

```toml
[model_providers.proxy]
name = "OpenAI using LLM proxy"
base_url = "https://proxy.example.com/v1"
wire_api = "responses"

[model_providers.proxy.auth]
command = "/usr/local/bin/fetch-codex-token"
args = ["--audience", "codex"]
timeout_ms = 5000
refresh_interval_ms = 300000
```

该认证命令不接收 `stdin`，必须把 token 打印到 stdout。Codex 会去除首尾空白，空 token 视为错误，并按 `refresh_interval_ms` 主动刷新；设 `refresh_interval_ms = 0` 表示仅在认证重试后刷新。不要把 `[model_providers.<id>.auth]` 与 `env_key`、`experimental_bearer_token` 或 `requires_openai_auth` 混用。

#### Amazon Bedrock 提供商

Codex 内置 `amazon-bedrock` 提供商，直接设为 `model_provider` 即可；与自定义提供商不同，该内置提供商仅支持嵌套的 AWS profile 与 region 覆盖。

```toml
model_provider = "amazon-bedrock"
model = "<bedrock-model-id>"

[model_providers.amazon-bedrock.aws]
profile = "default"
region = "eu-central-1"
```

省略 `profile` 时 Codex 使用标准 AWS 凭据链。把 `region` 设为应处理请求的受支持 Bedrock 区域。完整流程、认证选项、支持模型与特性可用性见 Use ChatGPT Work and Codex with Amazon Bedrock（站内路径 /docs/amazon-bedrock）。

### OSS 模式（本地提供商）

传入 `--oss` 时，Codex 可对本地「开源」提供商运行，如 Ollama 或 LM Studio。单次运行用 `--local-provider` 选一个，或把 `oss_provider` 设为默认。两者都未设时，交互 CLI 会提示选择；`codex exec` 则报错退出。

```toml
# 配合 `--oss` 使用的默认本地提供商
oss_provider = "ollama" # or "lmstudio"
```

### Azure 提供商与按提供商调优

```toml
[model_providers.azure]
name = "Azure"
base_url = "https://YOUR_PROJECT_NAME.openai.azure.com/openai"
env_key = "AZURE_OPENAI_API_KEY"
query_params = { api-version = "2025-04-01-preview" }
wire_api = "responses"
request_max_retries = 4
stream_max_retries = 10
stream_idle_timeout_ms = 300000
```

要改内置 OpenAI 提供商的 base URL，用 `openai_base_url`；不要新建 `[model_providers.openai]`，因为不能覆盖内置提供商 ID。

### 使用数据驻留的 API 组织

开启数据驻留的项目可建模型提供商，按正确前缀更新 `base_url`。对开启数据驻留的 ChatGPT 工作区，无需自定义提供商；用 ChatGPT 登录时 Codex 会遵守工作区驻留设置。

```toml
model_provider = "openaidr"
[model_providers.openaidr]
name = "OpenAI Data Residency"
base_url = "https://us.api.openai.com/v1" # 把 'us' 换成域名前缀
```

### 模型推理、冗长度与限制

```toml
model_reasoning_summary = "none"          # 禁用摘要
model_verbosity = "low"                    # 缩短响应
model_supports_reasoning_summaries = true # 强制推理
model_context_window = 128000              # 上下文窗口大小
```

`model_verbosity` 仅对使用 Responses API 的提供商生效；Chat Completions 提供商会忽略它。

### 审批策略与沙箱模式

选择审批严格度（影响 Codex 何时暂停）与沙箱级别（影响文件/网络访问）。编辑 `config.toml` 的指引见 Common sandbox and approval combinations、Protected paths in writable roots 与 Network access（站内路径 /docs/agent-approvals-security）。

Codex 与 ChatGPT Work 不再支持 `approval_policy = "untrusted"`。迁移见 Migrate from the retired `untrusted` approval policy。同时配置文件系统与网络访问的 beta 权限 Profile 见 Permissions（站内路径 /docs/permissions），本资料集对应 [权限与安全](08-权限与安全.md)。

也可用细粒度审批策略（`approval_policy = { granular = { ... } }`）允许或自动拒绝个别提示类别：某些情况保留正常交互审批，而 `request_permissions` 或 skill 脚本提示等则自动失败关闭。

设 `approvals_reviewer = "auto_review"` 可把符合条件的交互审批请求路由到自动审查。这改变的是审查者，不是沙箱边界。本地审查策略说明用 `[auto_review].policy`；受管 `guardian_policy_config` 优先。

```toml
approval_policy = "on-request"  # 其他选项：never 或 { granular = { ... } }
approvals_reviewer = "user"     # 或 "auto_review" 走自动审查
sandbox_mode = "workspace-write"
allow_login_shell = false       # 可选加固：shell 工具禁用登录 shell

# 细粒度审批策略示例：
# approval_policy = { granular = {
#   sandbox_approval = true,
#   rules = true,
#   mcp_elicitations = true,
#   request_permissions = false,
#   skill_approval = false
# } }

[sandbox_workspace_write]
exclude_tmpdir_env_var = false  # 允许 $TMPDIR
exclude_slash_tmp = false       # 允许 /tmp
writable_roots = ["/Users/YOU/.pyenv/shims"]
network_access = false          # 显式允许出站网络

[auto_review]
policy = """
Use your organization's automatic review policy.
"""
```

#### 命名权限 Profile

内置 Profile、自定义 Profile 语法与完整文件系统/网络配置模型见 Permissions（站内路径 /docs/permissions）。完整键清单与要求约束见本页「配置参考」与 Managed configuration（站内路径 /docs/enterprise/managed-configuration）。

在 workspace-write 模式下，某些环境即使工作区其余部分可写，仍把 `.git/`、`.agents/`、`.codex/`、`.aws/` 保持只读。这就是为什么 `git commit` 之类命令在沙箱外仍可能需要审批。若想让 Codex 跳过特定命令（例如在沙箱外阻止 `git commit`），使用 rules（站内路径 /docs/agent-configuration/rules）。

完全关闭沙箱（仅当你的环境已隔离进程时使用）：

```toml
sandbox_mode = "danger-full-access"
```

### Shell 环境策略

`shell_environment_policy` 控制 Codex 传给派生命令的环境变量。用 `inherit = "none"` 从空环境开始，或用 `inherit = "core"` 继承裁剪后的集合；再加显式值与键过滤，避免把不必要的密钥传给派生命令。

```toml
[shell_environment_policy]
inherit = "core"
set = { MY_FLAG = "1" }
ignore_default_excludes = false

[shell_environment_policy.filters]
"AWS_*" = "exclude"
"AZURE_*" = "exclude"
```

过滤模式大小写不敏感，支持 `*` 与 `?`。用 `"exclude"` 移除匹配变量；当任一模式用 `"include"` 时，Codex 只保留匹配 include 模式的变量。include 不会恢复已被 exclude 的变量。过滤键跨配置层按大小写不敏感合并。

`ignore_default_excludes` 默认 `true`，因此 Codex 不会自动移除含 `KEY`、`SECRET`、`TOKEN` 的变量名；设 `false` 则在你的显式过滤之前先应用这些自动排除。Codex 先应用自动排除，再自定义排除、`set` 的值，最后是 include 白名单。由于 `set` 在排除之后运行，它可以恢复一个被排除的变量，但 include 白名单仍可移除该恢复值。

旧的 `exclude` 与 `include_only` 数组仍为既有配置保留。不要在同一配置层把这两个数组与 `[shell_environment_policy.filters]` 混用，Codex 会拒绝该组合。

### 可观测性与遥测

启用 OpenTelemetry（OTel）日志导出以跟踪 Codex 运行（API 请求、SSE/事件、提示、工具审批/结果）。默认关闭，通过 `[otel]` 开启：

```toml
[otel]
environment = "staging"   # 默认 "dev"
exporter = "none"         # 设为 otlp-http 或 otlp-grpc 才发送事件
log_user_prompt = false    # 除非显式开启，否则脱敏用户提示
```

选择导出器：

```toml
[otel]
exporter = { otlp-http = {
  endpoint = "https://otel.example.com/v1/logs",
  protocol = "binary",
  headers = { "x-otlp-api-key" = "${OTLP_TOKEN}" }
}}
```

```toml
[otel]
exporter = { otlp-grpc = {
  endpoint = "https://otel.example.com:4317",
  headers = { "x-otlp-meta" = "abc123" }
}}
```

若 `exporter = "none"`，Codex 记录事件但不发送。导出器异步批处理、关闭时冲刷。事件元数据含服务名、CLI 版本、env 标签、会话 id、模型、沙箱/审批设置与每事件字段。

#### 会发出的内容

Codex 为运行与工具使用发出结构化日志事件，代表性事件类型：

- `codex.conversation_starts`（模型、推理设置、沙箱/审批策略）
- `codex.api_request`（尝试次数、状态/成功、耗时、错误细节）
- `codex.sse_event`（流事件种类、成功/失败、耗时，`response.completed` 上含 token 计数）
- `codex.websocket_request` 与 `codex.websocket_event`（请求耗时及每消息种类/成功/错误）
- `codex.user_prompt`（长度；除非显式开启，内容脱敏）
- `codex.tool_decision`（批准/拒绝，以及决定来自配置还是用户）
- `codex.tool_result`（耗时、成功、输出片段）

### 通知

用 `notify` 在 Codex 发出受支持事件（目前仅 `agent-turn-complete`）时触发外部程序。适合桌面通知、chat webhook、CI 更新或内置 TUI 通知未覆盖的旁路告警。

```toml
notify = ["python3", "/path/to/notify.py"]
```

响应 `agent-turn-complete` 的示例 `notify.py`（节选）：

```python
#!/usr/bin/env python3
import json, subprocess, sys

def main() -> int:
    notification = json.loads(sys.argv[1])
    if notification.get("type") != "agent-turn-complete":
        return 0
    title = f"Codex: {notification.get('last-assistant-message', 'Turn Complete!')}"
    message = " ".join(notification.get("input-messages", []))
    subprocess.check_output([
        "terminal-notifier",
        "-title", title,
        "-message", message,
        "-group", "codex-" + notification.get("thread-id", ""),
        "-activate", "com.googlecode.iterm2",
    ])
    return 0

if __name__ == "__main__":
    sys.exit(main())
```

脚本接收单个 JSON 参数，常见字段：`type`（当前为 `agent-turn-complete`）、`thread-id`、`turn-id`、`cwd`、`input-messages`、`last-assistant-message`。把脚本放在磁盘某处并让 `notify` 指向它。

`notify` 与 `tui.notifications` 的区别：`notify` 运行外部程序（适合 webhook、桌面通知器、CI hook）；`tui.notifications` 内置于 TUI，可按事件类型过滤；`tui.notification_method` 控制 TUI 如何发终端通知（`auto`、`osc9`、`bel`）；`tui.notification_condition` 控制 TUI 通知仅在终端 `unfocused` 时还是 `always` 触发。`auto` 模式下 Codex 优先 OSC 9 通知，否则回退 BEL（`\x07`）。

### 历史持久化

默认 Codex 把本地会话记录保存在 `CODEX_HOME` 下（如 `~/.codex/history.jsonl`）。关闭本地历史持久化：

```toml
[history]
persistence = "none"
```

限制历史文件大小，设 `history.max_bytes`；文件超过上限时 Codex 丢弃最旧条目并压缩文件、保留最新记录。

```toml
[history]
max_bytes = 104857600 # 100 MiB
```

### 可点击引用

若使用支持它的终端/编辑器集成，Codex 可把文件引用渲染为可点击链接。配置 `file_opener` 选择 URI scheme：

```toml
file_opener = "vscode" # or cursor, windsurf, vscode-insiders, none
```

例如 `/home/user/project/main.py:42` 可改写为可点击的 `vscode://file/...:42` 链接。

### 项目指令发现

Codex 读取 `AGENTS.md`（及相关文件），并在会话首轮带入有限的项目指引。两个旋钮控制：`project_doc_max_bytes`（每个 `AGENTS.md` 读多少字节）与 `project_doc_fallback_filenames`（某层缺少 `AGENTS.md` 时尝试的额外文件名）。详细走查见 Custom instructions with AGENTS.md（站内路径 /docs/agent-configuration/agents-md）。

### 桌面端

#### 添加自定义文件处理器

在用户级 `~/.codex/config.toml` 的 `desktop.custom_file_handlers` 下添加条目，用桌面应用默认不支持的编辑器或内部启动器打开文件。每个条目在应用的 **Open in** 菜单中增加一个编辑器目标；当 `command` 是已存在的绝对路径或能从应用 `PATH` 解析时，应用会列出该目标。下例展示三种传文件方式：

```toml
# 把打开的路径直接追加到命令后。
[desktop.custom_file_handlers.vscodium]
label = "VSCodium"
icon = "/Users/you/.codex/icons/vscodium.png"
command = "codium"

# 在打开的路径前放固定参数。
[desktop.custom_file_handlers.textedit]
label = "TextEdit"
icon = "/Users/you/.codex/icons/textedit.png"
command = "/usr/bin/open"
args = ["-a", "TextEdit"]

# 追加一个含路径与编辑器上下文的 JSON 参数。
[desktop.custom_file_handlers.company_editor]
label = "Company Editor"
icon = "/opt/company/editor/icon.png"
command = "/opt/company/bin/editor"
input = "json_argument"
```

保存 `config.toml` 后重启 ChatGPT 桌面应用。处理器 ID 是 TOML 表头的最后一段，须含 1–64 字符、以 ASCII 字母或数字开头，其余仅含 ASCII 字母、数字、句点、下划线或连字符。应用以 `custom:` 前缀暴露该 ID，如 `company_editor` 变为 `custom:company_editor`。ID 含句点时需加引号以免 TOML 解析为嵌套表。

每个处理器支持的字段：

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `label` | 是 | 应用中显示名。 |
| `icon` | 是 | 打包应用图标（如 `apps/vscode.png`）、base64 `data:image/...` URL、`file:` URI 或绝对本地图片路径；不支持的来源用默认 VS Code 图标。 |
| `command` | 是 | 要检测并启动的可执行路径或命令名。 |
| `args` | 否 | 插入在 `command` 与文件输入之间的字符串数组，默认 `[]`。 |
| `input` | 否 | 应用如何发送文件输入：`path`、`json_argument` 或 `json_stdin`，默认 `path`。 |
| `supports_ssh` | 否 | 是否对 SSH 工作区中的文件提供该处理器，默认 `false`；需要远程主机与路径细节时用 `json_stdin`。 |

`input` 决定 `args` 之后的内容：`path` 把路径作为最后命令参数追加；`json_argument` 追加含 `target`、`path`、`appPath`、`location` 的 JSON 对象（`location` 为含 1 基 `line`、`column` 的对象或 `null`）；`json_stdin` 把该 JSON 对象写入标准输入而非加参数，并额外含 `hostConfig`、`remoteWorkspaceRoot`、`remotePath`（不适用时为 `null`）。把自定义处理器选为首选编辑器的持久化方式与选内置编辑器一致，含按项目偏好。

### TUI 选项

不带子命令运行 `codex` 即启动交互式终端 UI（TUI）。Codex 在 `[tui]` 下暴露部分 TUI 专用配置：

- `tui.notifications`：启用/禁用通知（或限制到特定类型）
- `tui.notification_method`：选 `auto`、`osc9`、`bel`
- `tui.notification_condition`：选 `unfocused` 或 `always`
- `tui.animations`：启用/禁用 ASCII 动画与 shimmer 效果
- `tui.alternate_screen`：控制备用屏使用（设 `never` 保留终端回滚缓冲）
- `tui.show_tooltips`：显示或隐藏欢迎屏的上手提示

`tui.notification_method` 默认 `auto`；`auto` 模式下若终端看似支持 OSC 9 则优先 OSC 9 通知，否则回退 BEL（`\x07`）。完整键清单见下节「配置参考」。

## 环境变量

原文存档：[source/environment-variables.md](source/environment-variables.md)

Codex 用 `config.toml` 保存持久设置，而环境变量用于 shell 级覆盖、自动化密钥、安装器行为或诊断。本页列出 Codex 直接读取的稳定公开环境变量；不列出内部开发变量、测试变量，以及你用 `env_key` 自选的提供商专属密钥名。

### 核心位置

| 变量 | 使用方 | 默认值 | 说明 |
| --- | --- | --- | --- |
| `CODEX_HOME` | CLI、IDE 扩展、app-server、安装器 | `~/.codex` | 设置 Codex 状态根，含配置、认证、日志、会话、skills 与独立包元数据；设置后该目录必须已存在。 |
| `CODEX_SQLITE_HOME` | CLI 与 app-server 状态 | `CODEX_HOME` | 设置 SQLite 后端状态存放位置；`sqlite_home` 配置键优先；相对路径相对当前工作目录解析。 |

`CODEX_HOME` 下文件见本页「高级配置」中「配置与状态位置」。

### 安装器变量

这些变量作用于 `https://chatgpt.com/codex/install.sh` 与 `https://chatgpt.com/codex/install.ps1` 提供的独立安装脚本。

| 变量 | 默认值 | 说明 |
| --- | --- | --- |
| `CODEX_NON_INTERACTIVE` | `false` | 设为 `1`、`true` 或 `yes` 跳过安装器提示；提示采用默认响应，用于脚本化安装与更新，而非首次运行设置。 |
| `CODEX_INSTALL_DIR` | macOS/Linux 为 `~/.local/bin`；Windows 为 `%LOCALAPPDATA%\Programs\OpenAI\Codex\bin` | 改变可见 `codex` 命令的安装位置；独立包缓存仍在 `CODEX_HOME/packages/standalone`。 |

无人值守安装时，在运行下载安装器的 shell 上设 `CODEX_NON_INTERACTIVE=1`：

```bash
curl -fsSL https://chatgpt.com/codex/install.sh | CODEX_NON_INTERACTIVE=1 sh
```

```powershell
$env:CODEX_NON_INTERACTIVE=1; irm https://chatgpt.com/codex/install.ps1 | iex
```

### 认证与网络

| 变量 | 使用方 | 说明 |
| --- | --- | --- |
| `CODEX_API_KEY` | exec、review、TypeScript SDK、远程 exec-server | 向非交互 Codex 进程提供 API key；在运行仓库受控代码时内联设置，而非全作业范围设置。 |
| `CODEX_ACCESS_TOKEN` | CLI、app-server、受信自动化 | 为受信自动化提供 ChatGPT 或 Codex 访问 token；持久登录用管道传给 `codex login --with-access-token`。 |

### 诊断

| 变量 | 使用方 | 说明 |
| --- | --- | --- |
| `RUST_LOG` | CLI 与 app-server | 控制 Rust 日志过滤与冗长度；除非设更详细值，`codex exec` 默认输出 `error`。 |

`RUST_LOG` 接受 `error`、`warn`、`info`、`debug`、`trace`，也接受更有针对性的 Rust 日志过滤器，如 `codex_core=debug,codex_tui=debug`。

交互 CLI 默认把诊断记录在有界本地存储中，但明文 `codex-tui.log` 文件是 opt-in。需要明文日志排障时显式设 `log_dir`：

```bash
RUST_LOG=debug codex -c log_dir=./.codex-log
tail -F ./.codex-log/codex-tui.log
```

非交互模式下，`codex exec` 内联打印消息，而不写入单独的 TUI 日志文件。
