# 08 权限与安全

本页汇总 Codex CLI 在本机侧的权限与安全模型：权限 Profiles（文件系统与网络边界）、Agent 审批策略与沙箱（何时必须停下询问）、以及身份验证（登录方式、凭据存储与无头环境登录）。三者叠加构成本机执行的最小信任边界，企业管理员还可通过受管配置进一步收紧。相关上下文另见 [07-环境与沙箱](07-环境与沙箱.md)、[06-Agent配置](06-Agent配置.md) 与 [05-配置-高级与参考](05-配置-高级与参考.md)。

## 权限 Profiles

原文存档：[source/permissions.md](source/permissions.md)

> 本节对应英文原文 `Permissions` 页（Beta，权限 Profiles 正在快速演进，可能随时变动）。

权限 Profiles 是一组命名策略，把"文件系统规则"（命令能读/写哪些路径）与"网络规则"（命令能访问哪些目标）组合在一起，用于在本机对 Codex 代你执行的本地命令施加最小权限边界。

**与旧沙箱设置的互斥关系**：权限 Profiles 不与旧的沙箱设置叠加使用。二者择其一：

- 要么配置 `default_permissions` 与 `[permissions]`；
- 要么配置 `sandbox_mode` / `sandbox_workspace_write`。

如果任一已加载配置文件中出现 `sandbox_mode`、你传入了 `--sandbox`、或所选 profile 设置了 `sandbox_mode`，Codex 就改用旧沙箱设置，而不是 `default_permissions`。受管 `allowed_permission_profiles` 是例外：它会强制 Codex 使用权限 Profiles；部署受管 profile 白名单前应先移除 `sandbox_mode`、`[sandbox_workspace_write]` 等旧设置。对混合版本的企业灰度，可临时保留 `allowed_sandbox_modes` 约束，直到所有客户端升级到 Codex 0.138.0 或更新版本。

**内置 Profiles**：

- `:read-only`：本地命令执行保持只读。
- `:workspace`：允许在当前工作区根与系统临时目录内写入。
- `:danger-full-access`：移除本地沙箱限制，仅在你明确需要这种宽泛访问时使用。

在 `[permissions.<name>]` 下创建命名 profile，再把顶层 `default_permissions` 指向该名称或上述内置名。示例中的 `project-edit` 是用户自定义名，不是内置值。企业管理员可通过受管 `requirements.toml` 定义 profile 并限制用户可选范围；一旦出现 `allowed_permission_profiles`，未列出的 profile（含未列出的内置项与未来版本新增项）一律拒绝。

自定义 profile 用到两个相关概念：

- `[permissions.<name>.workspace_roots]`：为该 profile 追加具体目录，作为"工作区根"。
- `[permissions.<name>.filesystem.":workspace_roots"]`：在所有生效工作区根（当前会话运行时根 + profile 自定义根）内统一套用的文件系统规则。

profile 同样遵循配置分层模型，高优先级层可在同名 profile 下追加或替换条目，而不必整段重写。例如组织级与用户级配置可独立扩展同一个 `server` profile：

```toml
# /etc/codex/config.toml
[permissions.server.workspace_roots]
"~/code/server" = true
```

```toml
# ~/.codex/config.toml
[permissions.server.workspace_roots]
"~/code/mobile-app" = true
```

当 `server` 生效时，两个工作区根同时进入生效 profile。

完整示例：

```toml
default_permissions = "project-edit"

[features]
network_proxy = true

[permissions.project-edit.workspace_roots]
"~/code/app" = true
"~/code/shared-lib" = true

[permissions.project-edit.filesystem]
":minimal" = "read"

[permissions.project-edit.filesystem.":workspace_roots"]
"." = "write"
".devcontainer" = "read"
"**/*.env" = "deny"

[permissions.project-edit.network]
enabled = true

[permissions.project-edit.network.domains]
"api.openai.com" = "allow"
"objects.githubusercontent.com" = "allow"
"*.github.com" = "allow"
"tracking.example.com" = "deny"
```

该 profile：读取常见开发工具所需的最小运行时路径；把同一工作区根规则同时套用到当前会话与 profile 自定义根；在每个根下把 `.devcontainer/` 等 IDE 相邻目录保持只读；用 glob 规则拒绝匹配的环境文件；仅通过配置的域名策略放行网络。

在生效 profile 内，更窄的 `deny` 规则始终有效，即使更宽的路径可读/可写。例如可让工作区根可写，同时把匹配的 `.env` 路径设为 `deny`。

### 继承现有 Profile

当某 profile 与内置或另一命名 profile 大体相同时，用 `extends`。优先继承内置 profile 而非从零开始，以便基线保护自动延续。例如继承 `:workspace` 会自动把工作区根下的 `.git`、`.agents`、`.codex`、`.aws` 保持只读，除非你显式覆盖。

```toml
default_permissions = "project-edit"

[features]
network_proxy = true

[permissions.project-edit]
description = "Project editing with OpenAI API access."
extends = ":workspace"

[permissions.project-edit.filesystem.":workspace_roots"]
"**/*.env" = "deny"

[permissions.project-edit.network]
enabled = true

[permissions.project-edit.network.domains]
"api.openai.com" = "allow"
```

该 profile 从 `:workspace` 起步，保持匹配的 `.env` 被拒绝，并允许访问 `api.openai.com`。profile 可继承 `:read-only`、`:workspace` 或另一命名 profile；不能继承 `:danger-full-access`；Codex 同时拒绝未知父级与继承环。

### 配置项速查（Profile 定义）

| 配置项 | 类型 / 取值 | 默认 | 说明 |
| --- | --- | --- | --- |
| `default_permissions` | 字符串 profile 名 | 无 | Codex 默认套用的 profile 名，须匹配 `[permissions]` 下某 profile 或内置名（如 `:workspace`）。显式设置以获得可预期行为；受管要求仅在 `:workspace` 与 `:read-only` 都被显式放行时才可省略。若无受管 `allowed_permission_profiles` 指示使用 profiles，Codex 仍回退到旧沙箱设置。 |
| `[permissions.<name>]` | 表 | 无 | 定义命名 profile。`default_permissions` 选其一作为默认；其他 profile 相关设置也用该名称。 |
| `permissions.<name>.description` | 字符串 | 无 | profile 的人类可读描述。通过 `extends` 不继承父级 description。 |
| `permissions.<name>.extends` | 字符串 profile 名 | 无 | 从另一命名 profile 或内置 `:read-only` / `:workspace` 起步。拒绝 `:danger-full-access`、未知父级与继承环。 |
| `[permissions.<name>.workspace_roots]` | 表 | 无 | 追加 profile 自定义工作区根，与当前会话运行时根一起接受 `:workspace_roots` 规则。 |
| `permissions.<name>.workspace_roots."<path>"` | boolean | `false` | 为 `true` 时把路径加入 profile 工作区根集合；`false` 项保持不激活。 |
| `[permissions.<name>.filesystem]` | 表 | 无 | 把文件系统路径映射到访问值或作用域子路径表。缺失或为空的 filesystem 表会保持文件系统访问受限并在启动时告警。 |
| `permissions.<name>.filesystem.glob_scan_max_depth` | 数字 | 无 | 在 Linux/WSL/原生 Windows 上，沙箱启动前快照匹配项时限制 deny-read glob 的展开深度。值越大启动扫描越重。使用无界 `**` 模式时至少设为 `1`。 |
| `[permissions.<name>.filesystem]."<path>"` | `read` / `write` / `deny` | 无 | 对受支持路径授予直接访问。`deny` 同时拒绝读写，且优先于同等具体的 `write` 或 `read`。运行时无法强制执行的直接 write 规则会被拒绝。 |
| `[permissions.<name>.filesystem."<path>"]."<subpath>"` | `read` / `write` / `deny` | 无 | 对 `<path>` 的后代授予访问。用 `.` 表示基路径；其他子路径必须是相对后代，不能含 `.` 或 `..` 组件。 |
| `[permissions.<name>.network]` | 表 | 无 | 配置命令网络访问与活动网络代理强制执行的策略。除非管理员受管网络要求已启动代理，否则需启用 `features.network_proxy`。 |
| `permissions.<name>.network.enabled` | boolean | `false` | 让 profile 内命令获得网络访问。**它不会启动网络代理**；无活动代理时命令可直连，不受域名限制。 |
| `[permissions.<name>.network.domains]` | 表 | 无 | 把主机模式映射到 `allow` 或 `deny`。仅在网络代理活动时生效。无 `allow` 项时代理阻断域名请求；deny 覆盖 allow。 |
| `permissions.<name>.network.domains."<pattern>"` | `allow` / `deny` | 无 | 支持精确主机、`*.example.com`（子域）、`**.example.com`（apex+子域）、`*`（仅 allow 全局通配）。主机模式会被 trim、小写化、去尾点、去端口/方括号。 |
| `[permissions.<name>.network.unix_sockets]` | 表 | 无 | Unix socket 白名单覆盖。仅用于 Docker 等本地集成。 |
| `permissions.<name>.network.unix_sockets."<path>"` | `allow` / `deny` | 无 | 把绝对 Unix socket 路径加入生效白名单（`allow`）或拒绝（`deny`）。deny 项从生效白名单中剔除。 |
| `permissions.<name>.network.proxy_url` | URL 字符串 | `http://127.0.0.1:3128` | 用于 `HTTP_PROXY`、`HTTPS_PROXY`、WebSocket 代理变量及相关工具代理变量的 HTTP 代理监听。 |
| `permissions.<name>.network.enable_socks5` | boolean | `true` | 启用 `ALL_PROXY` 与 FTP 代理变量所用的 SOCKS5 监听。 |
| `permissions.<name>.network.socks_url` | URL 字符串 | `http://127.0.0.1:8081` | SOCKS5 监听地址。 |
| `permissions.<name>.network.enable_socks5_udp` | boolean | `true` | SOCKS5 监听启用时是否开启 SOCKS5 UDP。 |
| `permissions.<name>.network.allow_upstream_proxy` | boolean | `true` | 允许网络沙箱代理对外请求沿用环境中的上游 `HTTP(S)_PROXY` 与 `ALL_PROXY`。 |
| `permissions.<name>.network.allow_local_binding` | boolean | `false` | 为 `true` 时关闭本地/私网守卫。为 `false` 时，`localhost`、`127.0.0.1` 等精确本地字面量必须显式加白，解析到本地/私网 IP 的主机名保持阻断。 |
| `permissions.<name>.network.dangerously_allow_non_loopback_proxy` | boolean | `false` | 允许代理监听绑定非回环地址。普通本地开发保持不设。 |
| `permissions.<name>.network.dangerously_allow_all_unix_sockets` | boolean | `false` | 在支持 Unix socket 代理的地方绕过白名单。这是一个宽泛的本地逃生口。 |

### 文件系统权限

取值只有三档：

| 访问值 | 含义 |
| --- | --- |
| `read` | 允许命令读取文件、列出目录；不能创建、修改、重命名、删除。 |
| `write` | 允许读与改，包括在 OS 允许时创建、重命名、删除。 |
| `deny` | 同时拒绝读写。用于在更宽的 `read`/`write` 授权中划出一条禁止子路径。 |

更具体的条目覆盖更宽条目；同一路径冲突时 `deny` 优先于 `write`，`write` 优先于 `read`。

支持的路径形态：

| 路径 | 含义 | 可作用域子路径 |
| --- | --- | --- |
| `:root` | 文件系统根 | 仅 `.` |
| `:minimal` | 常见工具所需的平台与运行时路径 | 仅 `.` |
| `:workspace_roots` | 当前会话工作区根 + 所有已启用的 profile 自定义工作区根 | 是 |
| `:tmpdir` | `$TMPDIR` 位置（若可用） | 仅 `.` |
| `:slash_tmp` | `/tmp`（若存在） | 仅 `.` |
| `/absolute/path` | 平台绝对路径（macOS/Linux/WSL 下如 `/path`，原生 Windows 下如 `C:\path`） | 是 |
| `~/path` | 当前用户 home 下路径 | 是 |

原生 Windows 上 home 相对路径也可用反斜杠，如 `~\work`。仅当 profile 确实需要宽泛读取覆盖时才用 `:root = "read"`。

嵌套子路径必须留在工作区根内；`../other-repo` 这类父级穿越会被拒绝。

#### 用精确路径或 glob 拒绝读取

对 Codex 不应读取的文件或子树用 `deny`，即使附近更宽的 profile 规则允许访问。精确路径适合 `~/.ssh` 这类稳定位置；glob 适合跨仓库位置不固定的敏感文件族。当 glob 位于 `:workspace_roots` 下时，Codex 按每个生效工作区根相对解释：

```toml
[permissions.project-edit.filesystem.":workspace_roots"]
"**/*.env" = "deny"
```

在 Linux、WSL、原生 Windows（MXC 或 `elevated`）上，deny-read glob 匹配在每个沙箱进程启动时枚举；之后新建的匹配文件不会加入该进程的 deny 列表，若其他权限允许则仍可读。该快照只持续到沙箱进程生命周期结束，不覆盖整个 Codex 会话。不要依赖 glob 在运行中的长生命周期进程里阻断新建文件。deny glob 作为 deny-read 规则受支持；`read`/`write` glob 在 Linux/WSL/原生 Windows 沙箱上可移植性较差，优先用精确路径或 `"docs/**" = "read"` 这类子树规则。

使用无界 `**` deny-read 模式时需配 `glob_scan_max_depth`：

```toml
[permissions.project-edit.filesystem]
glob_scan_max_depth = 3

[permissions.project-edit.filesystem.":workspace_roots"]
"**/*.env" = "deny"
```

`glob_scan_max_depth` 至少为 `1`；值越大沙箱启动前扫描越深。若不想做有界展开，可显式列深度：`*.env`、`*/*.env`、`*/*/*.env`。

### 网络权限

网络访问与网络过滤是两个独立开关：`permissions.<name>.network.enabled = true` 让命令能联网，`features.network_proxy = true` 才强制执行 profile 的域名规则。

```toml
[features]
network_proxy = true

[permissions.project-edit.network]
enabled = true

[permissions.project-edit.network.domains]
"example.com" = "allow"      # exact host
"*.example.com" = "allow"    # subdomains only
"**.example.com" = "allow"   # apex and subdomains
"ads.example.com" = "deny"   # deny wins over allow
```

行为组合：

- 网络关：无论代理 feature 如何，命令都不能联网。
- 网络开、代理关：命令直连，不受限；profile 域名规则不生效。
- 网络开、代理开：命令走代理，代理强制执行 profile 域名规则；无 allow 项时阻断外部目标。

添加 `[permissions.<name>.network.domains]` 或 `network.enabled = true` **不会**自动启用 `features.network_proxy`。管理员也可通过 `requirements.toml` 的 `[experimental_network]` 启用代理。

活动代理默认绑定本地监听：

```toml
[permissions.project-edit.network]
enabled = true
proxy_url = "http://127.0.0.1:3128"
enable_socks5 = true
socks_url = "http://127.0.0.1:8081"
enable_socks5_udp = true
```

除非与特定运行时集成，否则保持默认。`dangerously_*` 是为特殊环境准备的逃生口，普通本地开发不要用。

#### 本地与私网

网络代理活动时，Codex 默认启用本地/私网守卫，防御 DNS rebinding 与误访本地服务。要显式放行某个本地目标，把精确主机或 IP 字面量加白：

```toml
[permissions.project-edit.network.domains]
"localhost" = "allow"
"127.0.0.1" = "allow"
```

仅当 profile 必须访问解析到本地/私网地址的已加白主机名时，才设 `allow_local_binding = true`。

#### Unix sockets

Unix socket 代理是给 Docker 等工具用的本地逃生口，慎用：

```toml
[permissions.project-edit.network.unix_sockets]
"/var/run/docker.sock" = "allow"
"/tmp/old.sock" = "deny"
```

启用 Unix sockets 时，代理监听保持绑定回环地址。

### 从旧沙箱设置迁移

权限 Profiles 用于在你想用一条可复用 profile 同时描述文件系统与网络行为时，取代旧的 `sandbox_mode` + `sandbox_workspace_write` 组合。同一会话只用一套。

建议起点：

- 只读工作流：用内置 `:read-only`，或定义只在需要处给 read 的自定义 profile。
- 工作区编辑：用内置 `:workspace`，或自定义 profile 通过 `:workspace_roots` 写入，仅追加工作流需要的额外临时/缓存路径。
- 不受限本地执行：仅在你确实想要最宽本地访问模型时用 `:danger-full-access`。

Profile 描述会话的本地默认姿态；组织受管 requirements 仍可叠加用户配置不应放宽的限制。

### 作用域与执行机制

- Profile 只约束**本机沙箱内命令执行**。Connectors、MCP servers、浏览器/Computer Use、Codex Cloud 环境设置与已批准的提权各有自己的控制面。
- 写能力 profile 会产生持久变更：对脚本、构建步骤、包管理器 hooks、shell 启动文件、共享目录的写入都应视为敏感，因为后续工具或用户可能在原始沙箱上下文之外执行它们。
- 网络域名规则只在网络代理活动时约束沙箱命令的外发流量；它不判定目标是否可信，通配 allow 仍然很宽。
- 活动网络代理默认阻断本地/私网目标；显式加白 `localhost`、私网 IP、Unix socket，或设 `allow_local_binding = true` 才打开。

网络代理**不**过滤：Web 搜索（由 `web_search` 与受管 `allowed_web_search_modes` 控制）、Apps/Connectors、MCP servers、浏览器与 Computer Use、Codex 模型与鉴权等客户端服务流量、Codex Cloud 任务（其环境自带网络设置）。命令网络白名单不是 Codex 一切动作的全局网络策略。

各平台执行机制：

- macOS：Seatbelt 沙箱 profile；平台沙箱无法强制执行所选策略时，Codex 拒绝运行该命令，而不是静默无沙箱运行。
- Linux/WSL：用 bubblewrap + seccomp 强制文件系统限制；旧 Landlock 选项无法隔离 app-server Unix socket，会被文件系统受限策略拒绝，升级时关闭 `features.use_legacy_landlock`。阻断 bubblewrap 所需操作的主机无法运行这些策略。
- Windows：MXC 用进程隔离做文件系统与网络权限；旧 `elevated` 回退用低权限沙箱用户、文件系统权限边界与防火墙规则；`unelevated` 是更弱的旧回退，网络隔离更弱，不能执行所有 split read/write 切割，不支持的策略会被拒绝。需要 Linux 沙箱模型时用 WSL。

### 常见 Profile 示例

只读 + 网络白名单：

```toml
default_permissions = "readonly-net"

[features]
network_proxy = true

[permissions.readonly-net.filesystem]
":minimal" = "read"

[permissions.readonly-net.filesystem.":workspace_roots"]
"." = "read"

[permissions.readonly-net.network]
enabled = true

[permissions.readonly-net.network.domains]
"api.openai.com" = "allow"
```

文件访问仅限工作区：

```toml
default_permissions = "workspace-only"

[permissions.workspace-only]
# By extending the :workspace profile, you get Codex's safeguards to ensure
# paths such as .git/, .agents/, .codex/, and .aws/ within a workspace root
# are read-only while the rest of the folder is writable.
extends = ":workspace"

[permissions.workspace-only.filesystem]
# By default, deny read access to all files on disk.
":root" = "deny"

# Though in practice, a software agent needs to be able to read folders that
# contain common tools, such as `/usr/bin`, to get work done, so grant access
# to a "minimal" set of files and folders, as determined by Codex.
":minimal" = "read"

# By extending the :workspace profile, :tmpdir and :slash_tmp are "write" by
# default, though you can deny access to them altogether, if desired.
":tmpdir" = "deny"
":slash_tmp" = "deny"
```

工作区可写、断网：

```toml
default_permissions = "project-edit"

[permissions.project-edit.filesystem]
":minimal" = "read"

[permissions.project-edit.filesystem.":workspace_roots"]
"." = "write"

[permissions.project-edit.network]
enabled = false
```

工作区可写 + 公网：

```toml
default_permissions = "workspace-net"

[features]
network_proxy = true

[permissions.workspace-net.filesystem]
":minimal" = "read"

[permissions.workspace-net.filesystem.":workspace_roots"]
"." = "write"

[permissions.workspace-net.network]
enabled = true

[permissions.workspace-net.network.domains]
"*" = "allow"
```

全局 `"*"` allow 仅在你确实要放公网时使用；deny 规则可收紧宽白名单。

## Agent 审批与安全

原文存档：[source/agent-approvals-security.md](source/agent-approvals-security.md)

Codex 默认关闭网络访问；本机上 OS 级沙箱把可触碰范围限制在当前工作区，并配一条审批策略，控制它在行动前何时必须停下询问你。

### 从已废弃的 `untrusted` 审批策略迁移

Codex 与 ChatGPT Work 不再支持 `approval_policy = "untrusted"`。该废弃设置可能阻止客户端启动，需从用户/项目配置、profile 文件、启动脚本与受管默认值中移除。交互式只读用法可改为：

```toml
sandbox_mode = "read-only"
approval_policy = "on-request"
```

或运行 `codex --sandbox read-only --ask-for-approval on-request`。`on-request` 下，沙箱允许的命令无需审批即可运行、可读可达文件、并在启用时使用网络。

若想保留更严的命令审批规则，省略显式 `approval_policy`，并在用户级 `~/.codex/config.toml` 加项目条目：

```toml
[projects."/path/to/project"]
trust_level = "untrusted"
```

此后命令需要审批，除非某执行策略规则放行；这同时禁用项目本地配置。显式设 `on-request` 会覆盖项目派生策略；受管 `allowed_approval_policies` 必须包含 `untrusted` 才允许该行为。

### 沙箱与审批：两层控制

Codex 安全控制来自两层协同：

- **沙箱模式（sandbox mode）**：Codex 执行模型生成命令时技术上能做什么（能写哪里、能否联网）。
- **审批策略（approval policy）**：Codex 在执行某动作前何时必须问你（离开沙箱、联网、在可信集合外跑命令）。

不同运行位置沙箱模式不同：

- **Codex Cloud（Legacy）**：跑在 OpenAI 托管的隔离容器中，访问不到宿主或无关数据；两阶段运行模型——setup 阶段可联网装依赖，agent 阶段默认离线，除非为该环境开启互联网访问；为云环境配置的 secrets 仅在 setup 阶段可用，agent 阶段开始前移除。
- **当前 Codex Cloud**：凭据在 setup 与任务期间的处理见其环境变量与网络 secrets 文档。
- **Codex CLI / IDE 扩展**：OS 级机制强制执行沙箱；默认无网络访问、写入限于当前工作区；可按风险偏好配置沙箱、审批策略与网络。

在 `Auto` 预设（如 `--sandbox workspace-write --ask-for-approval on-request`）下，Codex 可在工作目录内自动读文件、改文件、跑命令；要在工作区外改文件或跑需要联网的命令时才请求审批。若只想聊天/规划不改东西，用 `/permissions` 切到 `read-only`。

对声明了副作用的 app（connector）工具调用，即使不是 shell 命令或文件改动，Codex 也会请求审批。声明了 destructive annotation 的 app/MCP 调用始终需审批（除非该工具同时声明了 read annotation，后者优先）。

### 安全监控与暂停任务

GPT-6 Astra 在 Codex 与 ChatGPT Work 中内置安全监控。监控异步运行，检测到潜在不安全模型行为时可暂停任务；暂停可能在触发活动之后才到达。监控不替代沙箱、权限或结果审查。

任务被暂停时，阅读通知并在可用时审阅发现；确认可安全继续后再恢复。若通知说任务已结束或未提供恢复选项，则无法从该界面恢复。

| 界面与数据控制 | 发现与恢复 |
| --- | --- |
| Codex 与 ChatGPT Work 客户端（带发现与恢复流程，且未列数据控制） | 恢复前审阅发现。 |
| Codex CLI 与移动端 | 完整发现与恢复不可用，任务直接结束。 |
| 零数据保留、Modified Abuse Monitoring、或非美国数据存储驻留 | 完整发现与恢复不可用，任务直接结束。 |

安全监控评估任务期间的模型行为；自动审批评审（auto-review）评估本就需要审批的单个动作是否在运行前放行。被 auto-review 批准的动作仍可能属于一个后来被监控暂停的任务。

### 网络访问

默认 `workspace-write` 沙箱模式关闭网络，除非你在配置中显式开启：

```toml
[sandbox_workspace_write]
network_access = true
```

#### 网络隔离

受管 Codex Cloud 执行路径上，Agent Security 要求约束命令联网；Cloud 环境的互联网设置单独适用。Agent Security 里放行的域名不会覆盖 Cloud 环境互联网设置里的限制。这些命令网络控制本身不关闭托管 Web 搜索、apps 或 MCP。ChatGPT Work Cloud 有独立的能力权限，不继承 Agent Security 要求。

受管命令白名单作用于走受管代理的命令。策略允许且被批准的完整沙箱提权可绕过命令代理；窄网络授予 ≠ 完整沙箱提权。按预期边界配置强制执行的审批与沙箱要求，并同时测试普通与提权命令。

网络访问通过目标规则控制，作用于命令派生的脚本、程序与子进程。命令网络访问已开启时，打开 `network_proxy` feature 把流量约束到你配置的网络策略；加域名规则本身不会启用代理：

```toml
[features.network_proxy]
enabled = true
domains = { "api.openai.com" = "allow", "example.com" = "deny" }
```

一次性 CLI 会话：只需开关用布尔简写；同时设策略选项用表形式：

```bash
codex \
  -c 'features.network_proxy=true' \
  -c 'sandbox_workspace_write.network_access=true'

codex \
  -c 'features.network_proxy.enabled=true' \
  -c 'features.network_proxy.domains={ "api.openai.com" = "allow", "example.com" = "deny" }' \
  -c 'sandbox_workspace_write.network_access=true'
```

该 feature 改变"已开启的网络访问"如何强制执行，本身不授予网络访问。用 `sandbox_workspace_write.network_access` 配 `workspace-write` 决定命令到底有没有网络：

- 网络关 + `network_proxy` 开：网络仍关，feature 不生效。
- 网络开 + `network_proxy` 关：网络直连、出站不受限。
- 网络开 + `network_proxy` 开：网络保留，出站被配置的网络策略约束。

代理 feature 同样作用于权限 Profiles：profile 的 `network.enabled = true` 授予命令网络访问，`features.network_proxy = true` 才激活该 profile 域名规则的强制执行：

```toml
default_permissions = "project-edit"

[features]
network_proxy = true

[permissions.project-edit]
extends = ":workspace"

[permissions.project-edit.network]
enabled = true

[permissions.project-edit.network.domains]
"api.openai.com" = "allow"
```

省略代理 feature 时，命令直连，`api.openai.com` 的 allow 规则不约束目的地。管理员受管 `experimental_network` 要求与用户 feature 开关相互独立：它可以不依赖 `features.network_proxy` 就配置并启动沙箱联网，但活动沙箱本就关闭网络时它不会把网络打开。

#### 网络策略

域名规则白名单优先：

- 精确主机只匹配自身。
- `*.example.com` 匹配 `api.example.com` 等子域，不匹配 `example.com`。
- `**.example.com` 同时匹配 apex 与子域。
- 全局 `*` allow 匹配所有未被 deny 的公网主机；把 `*` 当宽泛网络访问，能限定就限定。
- `deny` 永远压过 `allow`；全局 `*` 仅对 allow 规则合法。

#### 本地与私网目标

默认 `allow_local_binding = false`，阻断环回、链路本地与私网目标：

- 精确例外：命令需要某个本地目标时，加精确本地 IP 字面量或 `localhost` allow 规则。
- 更宽访问：仅当你确实想要更宽本地/私网可达时，设 `allow_local_binding = true`。
- 通配：通配规则不算显式本地例外。
- 解析地址：解析到本地/私网 IP 的主机名即使匹配白名单也保持阻断。

#### DNS rebinding 防护

放行主机名前，Codex 尽力做 DNS 与 IP 分类检查：查询失败/超时被阻断；解析到非公网地址的主机名被阻断。该检查降低 DNS rebinding 风险但不消除；要彻底防 rebinding 需在传输层钉死解析 IP。若恶意 DNS 在威胁范围内，还要在更低层强制出站控制。

#### 危险设置

两个有意放宽信任边界的设置：

- `dangerously_allow_non_loopback_proxy = true`：可把代理监听暴露到环回之外。
- `dangerously_allow_all_unix_sockets = true`：绕过 Unix socket 白名单。

仅在严格受控环境使用。启用 Unix socket 代理时，监听保持仅环回，沙箱联网不会变成通往本地守护进程的远程桥。

`network_proxy` 默认关。开启后：

| 设置 | 默认 | 行为 |
| --- | --- | --- |
| `enabled` | `false` | 仅在命令网络访问已开时才启动沙箱联网。 |
| `domains` | 未设 | 白名单行为：加 `allow` 规则前不允许任何外部目标。支持精确主机、作用域通配与全局 `*` allow；`deny` 永远胜出。 |
| `unix_sockets` | 未设 | 加显式 `allow` 前不允许任何 Unix socket 目标。 |
| `allow_local_binding` | `false` | 阻断本地与私网目标，除非加精确本地 IP/`localhost` allow，或显式选择更宽本地/私网访问。 |
| `enable_socks5` | `true` | 策略允许时暴露 SOCKS5。 |
| `enable_socks5_udp` | `true` | SOCKS5 可用时允许 UDP over SOCKS5。 |
| `allow_upstream_proxy` | `true` | 让沙箱联网沿用环境上游代理。 |
| `dangerously_allow_non_loopback_proxy` | `false` | 监听端点保持环回，除非你刻意暴露到 localhost 之外。 |
| `dangerously_allow_all_unix_sockets` | `false` | Unix socket 访问保持白名单，除非你刻意绕过该保护。 |

#### 命令网络代理之外的流量

网络代理只过滤跑在本地命令沙箱内的脚本、程序与子进程；不过滤 Web 搜索、app/connector 工具调用、MCP server 连接、浏览器/Computer Use、Codex cloud 任务、以及客户端模型与鉴权请求。这些面各有独立的服务连接、feature 设置、工作区策略或环境控制。

浏览器工具在访问某 origin 前会单独检查受管网络 deny 与独占白名单；浏览器 origin 策略可进一步限制站点访问、上传、下载与开发者工具。受管用户应把命令网络策略与 `allowed_web_search_modes`、已批准的 `mcp_servers`、以及 apps/plugins/浏览器/Computer Use 的 feature 要求组合使用。

你也可以在不给派生命令完整网络访问的前提下控制 Web 搜索工具。Codex 默认用 Web 搜索缓存访问结果：缓存是 OpenAI 维护的索引，返回预索引结果而非实时抓取页面，降低来自任意实时内容的 prompt injection 暴露。把 Web 结果视为不可信。使用 `--yolo` 或其他完整访问沙箱设置时，Web 搜索默认走 live；用 `--search` 或 `web_search = "live"` 允许实时浏览，设 `"disabled"` 关闭：

```toml
web_search = "cached"  # default
# web_search = "disabled"
# web_search = "live"  # same as --search
```

外部 Web 访问需由搜索索引把关时设 `web_search = "indexed"`。在 Codex 中启用网络访问或 Web 搜索时务必谨慎：prompt injection 可让 agent 抓取并遵循不可信指令。

### 默认值与建议

- 启动时 Codex 检测目录是否受版本控制并推荐：
  - 受版本控制目录：`Auto`（工作区写 + on-request 审批）。
  - 未受版本控制目录：`read-only`。
- 视配置，Codex 可能以 `read-only` 启动，直到你显式信任工作目录（通过 onboarding 提示或 `/permissions`）。
- 工作区包含当前目录与 `/tmp` 等临时目录；用 `/status` 查看工作区目录列表。
- 接受默认值直接运行 `codex`；也可显式指定：
  - `codex --sandbox workspace-write --ask-for-approval on-request`
  - `codex --sandbox read-only --ask-for-approval on-request`

#### 可写根中的受保护路径

默认 `workspace-write` 沙箱策略下，可写根内仍有受保护路径：

- `<writable_root>/.git` 无论作为目录还是文件都保护为只读；
- 若 `<writable_root>/.git` 是指针文件（`gitdir: ...`），解析后的 Git 目录路径也保护为只读；
- `<writable_root>/.agents` 作为目录存在时保护为只读；
- `<writable_root>/.codex` 作为目录存在时保护为只读；
- `<writable_root>/.aws` 作为目录存在时保护为只读；
- 保护是递归的，这些路径下一切内容只读。

#### 关闭审批提示

用 `--ask-for-approval never` 或 `-a never`（简写）关闭审批提示。该选项与所有 `--sandbox` 模式配合，你仍控制 Codex 自主程度。

若需要 Codex 读文件、改文件、跑联网命令且无审批提示，用 `--sandbox danger-full-access`（或 `--dangerously-bypass-approvals-and-sandbox` 标志），务必谨慎。

折中：`approval_policy = { granular = { ... } }` 可让特定审批类别保持交互式、其余自动拒绝。granular 策略覆盖沙箱审批、execpolicy 规则提示、MCP 提示、`request_permissions` 提示与 skill 脚本审批。

#### 自动审批评审

默认审批请求路由给你：

```toml
approvals_reviewer = "user"
```

当审批是交互式的（如 `approval_policy = "on-request"` 或 granular 审批策略）时，可启用自动审批评审：把 `approvals_reviewer` 设为 `auto_review`，让符合条件的审批请求先经过一个评审 agent 再运行：

```toml
approval_policy = "on-request"
approvals_reviewer = "auto_review"
```

评审只评估本就需要审批的动作（沙箱提权、被阻断的网络请求、`request_permissions` 提示、有副作用的 app/MCP 调用）；留在沙箱内的动作无额外评审。评审策略检查数据外泄、凭据探测、持续性安全弱化与破坏性动作；低/中风险动作策略允许时可继续；关键风险动作被策略拒绝；高风险动作需足够用户授权且无匹配 deny 规则。prompt 构建、评审会话与解析失败时 fail closed；超时单独上报，动作仍不运行。

默认评审策略在开源 Codex 仓库的 `codex-rs/core/src/guardian/policy.md`。企业可在受管要求里用 `guardian_policy_config` 替换租户专属段；本地 `[auto_review].policy` 文本也受支持，但受管要求优先。ChatGPT 桌面应用中，这些评审显示为带 Reviewing / Approved / Denied / Aborted / Timed out 状态的自动评审项，可附风险等级与用户授权评估。自动评审消耗额外模型调用，管理员可用 `allowed_approvals_reviewers` 约束。

#### 常见沙箱与审批组合

| 意图 | 标志 / 配置 | 效果 |
| --- | --- | --- |
| Auto（预设） | 无需标志，或 `--sandbox workspace-write --ask-for-approval on-request` | Codex 可在工作区内读文件、改文件、跑命令；在工作区外改文件或联网需审批。 |
| 安全只读浏览 | `--sandbox read-only --ask-for-approval on-request` | Codex 可在只读沙箱内读文件、跑命令；沙箱外动作可能需审批。 |
| 只读非交互（CI） | `--sandbox read-only --ask-for-approval never` | Codex 在只读沙箱内读文件、跑命令；永不询问。 |
| Auto-review 模式 | `--sandbox workspace-write --ask-for-approval on-request -c approvals_reviewer=auto_review`，或 `approvals_reviewer = "auto_review"` | 沙箱边界同标准 on-request，但符合条件的审批请求由 auto-review 评审，不弹给用户。 |
| 危险完整访问 | `--dangerously-bypass-approvals-and-sandbox`（别名 `--yolo`） | 无沙箱；无审批（不推荐）。 |

非交互运行用 `codex exec --sandbox workspace-write`。

`config.toml` 示例：

```toml
# Interactive approvals with a read-only sandbox
approval_policy = "on-request"
sandbox_mode    = "read-only"
allow_login_shell = false # optional hardening: disallow login shells for shell-based tools

# Optional: Allow network in workspace-write mode
[sandbox_workspace_write]
network_access = true

# Optional: granular approval policy
# approval_policy = { granular = {
#   sandbox_approval = true,
#   rules = true,
#   mcp_elicitations = true,
#   request_permissions = false,
#   skill_approval = false
# } }
```

也可把预设存为 profile 文件，用 `codex --profile profile-name` 选用：

```toml
# ~/.codex/full_auto.config.toml
approval_policy = "on-request"
sandbox_mode    = "workspace-write"
```

```toml
# ~/.codex/readonly_quiet.config.toml
approval_policy = "never"
sandbox_mode    = "read-only"
```

# macOS
codex sandbox macos [--permissions-profile <name>] [--log-denials] [COMMAND]...
# Linux
codex sandbox linux [--permissions-profile <name>] [COMMAND]...

### OS 级沙箱

- macOS：用 Seatbelt 策略，通过 `sandbox-exec` 加对应 `--sandbox` 模式的 profile（`-p`）跑命令。受限读访问启用平台默认时，Codex 追加一份精选的 macOS 平台策略（而非宽泛放行 `/System`），以保留常见工具兼容性。
- Linux：默认 `bwrap` + `seccomp`。
- Windows：支持 MXC，`elevated` 与 `unelevated` 为旧回退。WSL2 中 Codex 用 Linux 沙箱实现；WSL1 通过 Codex `0.114` 支持，从 `0.115` 起 Linux 沙箱迁到 `bwrap`，WSL1 不再支持。

Windows 上的 Codex IDE 扩展直接支持 WSL2；在 VS Code 设置中加 `"chatgpt.runCodexInWindowsSubsystemForLinux": true`，让 agent 在 WSL2 可用时始终留在 WSL2 内，即使宿主是 Windows 也继承 Linux 沙箱语义。

Windows 上当设备与策略支持时，优先 MXC，在 `config.toml` 设：

```toml
[features]
prefer_mxc = true
```

在 `windows.sandbox` 保留一个受允许的旧实现作为回退。容器化环境（如 Docker）中，宿主或容器配置若阻断 namespace、setuid `bwrap` 或 `seccomp` 所需操作，沙箱可能失效；此时让 Docker 提供隔离边界，在容器内用 `--sandbox danger-full-access`（或 `--dangerously-bypass-approvals-and-sandbox`）运行。

在 Dev Containers 中运行 Codex 时：若宿主无法直接跑 Linux 沙箱、或组织已标准化容器化开发，让 Docker 提供外层隔离边界。Dev Containers 提供实质保护但不能挡住所有攻击；在容器内用 `--sandbox danger-full-access` 时，恶意项目可外泄容器内一切可用内容（含 Codex 凭据）。该模式仅用于可信仓库，并像其他提权环境一样监控 Codex 活动。容器内二选一：Dev Container profile 授予 `bwrap` 所需能力时保留 Codex Linux 沙箱；容器即预期安全边界时，在容器内跑 `--sandbox danger-full-access`，避免再叠一层沙箱。

### 版本控制建议

- 在 feature 分支上工作，委派前保持 `git status` 干净；便于隔离与回滚 Codex 补丁。
- 优先基于 patch 的工作流（`git diff` / `git apply`），而非直接编辑受跟踪文件；频繁提交以便小步回滚。
- 像对待 PR 一样对待 Codex 建议：跑针对性验证、审 diff、在提交信息里记录决策以便审计。

### 监控与遥测（OTel，opt-in）

Codex 默认关闭遥测；显式开启后通过 OpenTelemetry (OTel) 导出结构化日志事件，覆盖 chats、API 请求、SSE/WebSocket 流活动、用户提示（默认脱敏）、工具审批决策与工具结果。事件带 `service.name`、CLI 版本与环境标签（dev/staging/prod）。

```toml
[otel]
environment = "staging"   # dev | staging | prod
exporter = "none"          # none | otlp-http | otlp-grpc
log_user_prompt = false     # redact prompt text unless policy allows
```

```toml
[otel]
exporter = { otlp-http = {
  endpoint = "https://otel.example.com/v1/logs",
  protocol = "binary",
  headers = { "x-otlp-api-key" = "${OTLP_TOKEN}" }
}}
```

```toml
[otel]
exporter = { otlp-grpc = {
  endpoint = "https://otel.example.com:4317",
  headers = { "x-otlp-meta" = "abc123" }
}}
```

代表事件类型：`codex.conversation_starts`、`codex.api_request`、`codex.sse_event`、`codex.websocket_request`、`codex.websocket_event`、`codex.user_prompt`、`codex.tool_decision`、`codex.tool_result`；配套指标含 `codex.api_request`、`codex.sse_event`、`codex.websocket.request`、`codex.websocket.event`、`codex.tool.call`（及对应 `.duration_ms`）。

安全与隐私：除非策略明确允许存储提示内容，否则保持 `log_user_prompt = false`；遥测只路由到你控制的 collector；把工具参数与输出视为敏感；审视本地数据保留（`history.persistence` / `history.max_bytes`）；CLI 断网运行时 OTel 无法到达 collector，需在 `workspace-write` 模式为 OTel endpoint 放行网络，或在 Codex cloud 中导出并把 collector 域名加入白名单。OTel 是补充，不替代上述沙箱与审批保护。

企业管理员在受管配置（原文路径 `docs/enterprise/managed-configuration`）中为工作区配置 Codex 安全设置。

## 身份验证（登录选项）

原文存档：[source/auth.md](source/auth.md)

Codex 支持两种用 OpenAI 模型登录的方式：

- **用 ChatGPT 登录**：走订阅额度；
- **用 API key 登录**：走按量计费。

ChatGPT 桌面应用、Codex CLI 与 IDE 扩展在本地工作时都支持这两种方式；Codex cloud 仅支持用 ChatGPT 登录。登录方式同时决定适用的管理员控制与数据处理策略：

- 用 ChatGPT 登录时，Codex 用量遵循你的 ChatGPT 工作区权限、RBAC、以及 ChatGPT Enterprise 的保留与驻留设置。
- 用 API key 时，用量遵循 API 组织的保留与数据共享设置。

对受管工作区，身份验证只是访问的一层；工作区成员与 provisioning 决定谁能登录，seat 与工作区角色决定能用哪些产品面与功能。本地工作中，权限 Profiles 约束 agent 在设备上能做什么。

### 用 ChatGPT 登录

在 ChatGPT 桌面应用、Codex CLI、IDE 扩展中，登录流程会打开浏览器窗口；登录完成后浏览器把凭据返回给 Codex。

- Web：打开 ChatGPT 站点，登录，选择要工作的工作区；已认证会话保留在浏览器中。
- 桌面应用：在登出界面选 **Continue to sign in**，完成浏览器流程。
- Codex CLI：运行 `codex login`，完成浏览器流程；这是无有效会话时的默认认证路径。
- IDE 扩展：在登出界面选 **Sign in with ChatGPT**，完成浏览器流程。

要用 Local computer access with Work Cloud（跨桌面/移动/Web），需先用 ChatGPT 登录到合格工作区，再请工作区 owner 启用 Work Cloud 并打开 **Allow local computer access**。API key 与 Codex access token 不能启用 Local computer access with Work Cloud。

### 用 API key 登录

从 OpenAI 控制台获取 API key 后，也可在 ChatGPT 桌面应用、Codex CLI、IDE 扩展中用 API key 登录。

- 桌面应用：登出界面选 **Sign in another way**，输入 key，选 **Continue**。
- Codex CLI：通过 stdin 把 key 管道给 `codex login`：

```shell
printenv OPENAI_API_KEY | codex login --with-api-key
```

- IDE 扩展：登出界面选 **Use API Key**，输入 key，选 **OK**。

OpenAI 按标准 API 费率通过 OpenAI Platform 账户计费。API key 认证支持本地 Codex 工作流，但依赖 ChatGPT 工作区访问或云服务的某些功能受限或不可用。在 Codex CLI 与 ChatGPT 桌面应用中，API key 认证包含对 OpenAI 精选插件的访问；部分插件因连接流需要不支持的 OAuth 能力而不可用。用 API key 登录时，Codex 用标准 API 定价，而非 ChatGPT 套餐包含额度。API key 适合 CI/CD 等程序化 CLI 工作流；不要在不可信或公开环境中暴露 Codex 执行。

### 登录方式对比

| 维度 | 用 ChatGPT 登录 | 用 API key 登录 |
| --- | --- | --- |
| 计费 | ChatGPT 订阅额度（按套餐） | OpenAI Platform 标准 API 费率，按量 |
| 适用面 | ChatGPT 桌面应用、CLI、IDE 扩展本地工作；**Codex cloud 仅此方式** | 桌面应用、CLI、IDE 扩展本地工作；Codex cloud 不支持 |
| 数据/合规策略 | 跟随 ChatGPT 工作区权限、RBAC、Enterprise 保留与驻留 | 跟随 API 组织的保留与数据共享设置 |
| 企业能力 | 受工作区 RBAC、seat、角色、Work Cloud 本地访问等约束 | 部分依赖 ChatGPT 工作区/云服务的功能受限；插件能力受 OAuth 支持限制 |
| CLI 入口 | `codex login`（浏览器流程） | `printenv OPENAI_API_KEY \| codex login --with-api-key` |
| 典型用途 | 个人/团队日常交互式使用 | CI/CD、程序化自动化 |

### 查看认证状态或登出

- Web：打开 profile 菜单确认当前账户与工作区；选 **Log out** 结束浏览器会话。
- 桌面应用：profile 菜单查看当前账户或 API key 状态；选 **Log out** 清除凭据。
- CLI：运行 `codex login status` 查看当前认证方式；运行 `codex logout` 清除凭据。当进程选择 workload identity 时，`codex login` 与 `codex logout` 被拒绝，因为认证由进程环境控制。
- IDE 扩展：profile 菜单查看账户/key 状态；选 **Log out** 清除。

### 用 Codex access token 做企业自动化

ChatGPT Enterprise 工作区中，管理员可授予 access token 权限，让被许可成员为受信任、非交互式的 Codex 本地工作流创建 Codex access token。当自动化需要 ChatGPT 工作区访问、ChatGPT 托管的 Codex 权益、或企业工作区控制，且没有浏览器登录时，用 access token。Access token 面向受信任脚本、调度器与私有 CI runner；一般 OpenAI API 调用仍用 Platform API key。

CLI 中若环境已提供 access token，管道给 CLI：

```shell
printenv CODEX_ACCESS_TOKEN | codex login --with-access-token
```

### 保护 Codex cloud 账户

Codex cloud 直接与代码库交互，需要比其他 ChatGPT 功能更强的安全。请开启多因素认证（MFA）：

- 用社交登录（Google/Microsoft/Apple）不强制在 ChatGPT 账户上开 MFA，但可在社交登录提供商处设置。
- 通过 SSO 访问 ChatGPT 时，组织 SSO 管理员应面向所有用户强制 MFA。
- 用邮箱+密码登录的用户，访问 Codex cloud 前必须在账户上设置 MFA。
- 账户支持多种登录方式且其中之一是邮箱+密码时，即使你用其他方式登录，也必须先设 MFA 才能访问 Codex。

### 登录缓存

用 ChatGPT 或 API key 登录 ChatGPT 桌面应用、Codex CLI 或 IDE 扩展后，登录详情会被缓存并复用；CLI 与扩展共享同一份缓存登录。任一处登出，下次启动 CLI 或扩展都需重新登录。Codex 把登录详情以明文缓存在 `~/.codex/auth.json`，或放在操作系统的凭据存储中。ChatGPT 登录会话在使用期间自动刷新 token，活跃会话通常无需再次浏览器登录。

### 凭据存储

用 `cli_auth_credentials_store` 控制 CLI 把缓存凭据存在哪里：

```toml
# file | keyring | auto | ephemeral
cli_auth_credentials_store = "keyring"
```

| 取值 | 行为 |
| --- | --- |
| `file` | 凭据存在 `CODEX_HOME`（默认 `~/.codex`）下的 `auth.json`。 |
| `keyring` | 存在 OS 凭据存储；不可用时失败。 |
| `auto` | OS 凭据存储可用则用，否则回退 `auth.json`。 |
| `ephemeral` | 凭据仅驻留当前进程内存。 |

管理员可通过受管本地认证要求强制 `cli_auth_credentials_store` 与 `chatgpt_base_url`；用户不能通过 `config.toml` 或 CLI 覆盖。用文件存储时，把 `~/.codex/auth.json` 当密码对待：它含 access token，不要提交、不要贴进工单、不要在聊天里分享。

### 强制登录方式或工作区

受管环境中管理员可限制用户认证方式：

```toml
# Only allow ChatGPT login or only allow API key login.
forced_login_method = "chatgpt" # or "api"

# When using ChatGPT login, restrict users to a specific workspace.
forced_chatgpt_workspace_id = "00000000-0000-0000-0000-000000000000"
```

当前凭据不匹配配置限制时，Codex 登出用户并退出。

### CLI 登录诊断与自定义 CA

直接 `codex login` 会在配置的日志目录下写一份专门的 `codex-login.log`，用于调试浏览器登录或 device-code 失败，或在支持索取登录特定日志时提供。

若网络使用企业 TLS 代理或私有根 CA，登录前把 `CODEX_CA_CERTIFICATE` 指向 PEM bundle；未设时回退 `SSL_CERT_FILE`。同一套自定义 CA 设置同时作用于登录、普通 HTTPS 请求与安全 WebSocket 连接：

```shell
export CODEX_CA_CERTIFICATE=/path/to/corporate-root-ca.pem
codex login
```

### 无头设备登录

在远程/无头环境运行 CLI，或本地网络阻断 Codex 用于把 OAuth token 回传 CLI 的 localhost 回调时，浏览器登录 UI 可能不可用。优先用 device code 认证（beta）：在交互式登录 UI 选 **Sign in with Device Code**，或直接跑 `codex login --device-auth`。流程：

1. 在 ChatGPT 安全设置（个人账户）或 ChatGPT 工作区权限（工作区管理员）启用 device code 登录。
2. 在跑 Codex 的终端选 **Sign in with Device Code**，或运行 `codex login --device-auth`。
3. 在浏览器打开链接、登录、输入一次性 code。

device code 不可用时的回退：

- **回退 A：本地登录后拷贝认证缓存**。在一台有浏览器的机器上跑 `codex login`，确认 `~/.codex/auth.json` 存在，再把它拷到无头机器的 `~/.codex/auth.json`。把 `~/.codex/auth.json` 当密码对待。若 OS 把凭据存在凭据存储而非 `auth.json`，该方法不适用。
  - 经 SSH 拷贝：

    ```shell
    ssh user@remote 'mkdir -p ~/.codex'
    scp ~/.codex/auth.json user@remote:~/.codex/auth.json
    ```

    或一行避免 `scp`：

    ```shell
    ssh user@remote 'mkdir -p ~/.codex && cat > ~/.codex/auth.json' < ~/.codex/auth.json
    ```

  - 拷进 Docker 容器：

    ```shell
    # Replace MY_CONTAINER with the name or ID of your container.
    CONTAINER_HOME=$(docker exec MY_CONTAINER printenv HOME)
    docker exec MY_CONTAINER mkdir -p "$CONTAINER_HOME/.codex"
    docker cp ~/.codex/auth.json MY_CONTAINER:"$CONTAINER_HOME/.codex/auth.json"
    ```

  受信任 CI/CD runner 上该模式的进阶版见原文路径 `docs/auth/ci-cd-auth`：让 Codex 在正常运行中刷新 `auth.json` 并把更新后的文件留给下一作业；自动化仍推荐默认用 API key。

- **回退 B：经 SSH 转发 localhost 回调**。本地机与远程主机间可端口转发时，把 Codex 本地回调服务器（默认 `localhost:1455`）隧道出来：

  ```shell
  ssh -L 1455:localhost:1455 user@remote
  ```

  然后在该 SSH 会话里跑 `codex login`，在本地机器上跟随打印出的地址完成流程。

### 替代模型提供商的认证方式

在配置文件中定义自定义模型提供商时，可选择以下认证方式之一：

- **OpenAI 认证**：设 `requires_openai_auth = true`，可用 ChatGPT 或 API key 登录；适合通过 LLM 代理服务器访问 OpenAI 模型；此时 Codex 忽略 `env_key`。
- **环境变量认证**：设 `env_key = "<ENV_VARIABLE_NAME>"`，从名为 `<ENV_VARIABLE_NAME>` 的本地环境变量读取提供商专属 API key。
- **原生网关 OAuth**：配置 `[model_providers.<id>.gateway_oauth]`，通过组织身份提供商浏览器登录；与是否登录 ChatGPT 无关。
- **命令后端认证**：配置 `[model_providers.<id>.auth]`，从已安装的 credential helper 取 token。
- **无认证**：本地模型不需要凭据时，留空 `requires_openai_auth` 或设 `false`，并省略 `env_key`、`experimental_bearer_token`、`auth`、`gateway_oauth` 等凭据设置。
